# geo-software-build

プロダクト概要の「完成の条件」を満たすまで、実装とテストを人間を呼ばずに進める。技術の選定はここでは行わない (geo-software-arch、geo-software-infra、geo-software-data、geo-software-library の結果に従う)。手順は、地図アプリ 1 本を企画から公開まで通したときの記録から作った。その記録では、実装の合意から公開まで約 25 分、初めのコミットから公開まで 22 分だった。

| reference | 読むとき | 中身 |
|---|---|---|
| [order](references/order.md) | 作り始める前に | 小さく積む順番と、各段で書くテスト |
| [testing](references/testing.md) | テストの置き場所と道具を決めるとき | 本番と同じ実行環境でのテスト、配線のテスト、認証を通した通しの確認、画面の確かめ方 |
| [data](references/data.md) | 地図に載せるデータを組み立てるとき | 出典を固定した取得、行ごとの出典、ビルドで落とす検査、正本の決め方 |
| [pitfalls](references/pitfalls.md) | 詰まったとき、終わる前に | 実際に踏んだ失敗と、その見つけ方 |

## 入力

- プロダクト概要 (`product-brief.md`): 一行の説明、機能 (Must / Should / Could)、完成の条件、判断の方針、技術選定の結果、準備したもの。
- 完成の条件が無い、または人間がいないと判定できない形なら、昼なら聞き、夜なら機能の Must から受け入れの基準を自分で書き起こして「夜に決めたこと」に書く。
- 技術選定の結果が無ければ、先に技術選定のスキルを使う。

## 進め方

1. 完成の条件を、コードとは別のファイル (プロダクト概要の節、または `acceptance/` のような置き場所) に、確かめる手順として書き出す。テストを書き換えて条件を満たしたことにできないよう、実装の途中でこのファイルは直さない。直す必要が出たら「夜に決めたこと」に理由を書く。
2. リポジトリを作り、ライセンス (判断の方針か昼の合意に従う)、テストの道具、型検査、ビルドを最初に通す。テストの道具は本番の実行環境と同じものを選ぶ ([testing](references/testing.md))。
3. [order](references/order.md) の順に、テストを先に書いて小さく積む。1 段ごとにテスト、型検査、ビルドを通してコミットする。コミットは「何ができるようになったか」を書く。
4. 地図に載せるデータは、出典を固定して組み立て、行ごとに出典を持たせ、出典や帰属表示が欠けた行があればビルドを落とす ([data](references/data.md))。
5. 画面と同期の配線 (起動時の同期、認証の読み込み待ち、通信の時間切れ) もテストする。配線は依存を差し込めるモジュールに切り出す。純粋な関数とサーバーだけテストして配線を無テストで出すと、本番で壊れる ([pitfalls](references/pitfalls.md))。
6. 通しの確認は、利用者と同じ認証の経路で行う。外部の認証 SDK は、代役のスクリプトを通信の差し替えで遅らせて差し込む。複数の端末で使うものは、ブラウザの文脈を 2 つ作って端末 2 台に見立てる。
7. 画面をブラウザで開き、スクリーンショットを撮って自分の目で見る。地図は WebGL が要るので、ヘッドレスのブラウザでは WebGL を使える設定にする。数値で判定できるもの (地図の表示、マーカーの数、エラーの有無) は自動で確かめる。
8. 完成の条件を 1 つずつ確かめ、満たしたものと満たしていないものをプロダクト概要に書く。満たしたら geo-software-deploy に進む。

## 判断の原則

- 迷ったら判断の方針に従って決め、プロダクト概要の「夜に決めたこと」に理由と一緒に書く。人間に聞くために止まらない (昼は聞いてよい)。
- 既存の部品を使い回す。新しい部品 (独自のナビゲーション、独自のツールチップ、独自の現在地の表示) を作る前に、すでにある部品 (ページのヘッダー、ライブラリ標準のコントロール) で実現できないかを考える。
- 書けない人には操作を見せたまま無効にする (隠すと、何ができるサービスかが伝わらない)。非公開のデータは画面で隠すだけでなく、サーバーの読み出しで除く。
- エラーの文言は本当の原因を言う。地図の初期化の失敗を「データを読み込めませんでした」と出すと、利用者も次のエージェントも直し方を誤る。
- 秘密の値は会話にもログにも出さない。値を人間に渡す必要があるときは、人間が自分の端末で表示するコマンドを渡す。保存する合言葉はハッシュにする。公開してよい値 (Clerk の Publishable Key など) は設定ファイルに書いてよい。

## 出力

- 動くリポジトリ: テスト、型検査、ビルドが通る状態。README に、使い方、作り (構成と理由)、データの作り方と出典、開発の手順、ライセンスを書く。
- プロダクト概要の更新: 「技術選定の結果」の実装の節に、構成とテストの置き場所。完成の条件の達成状況。「夜に決めたこと」と「止まったこと」。

## 注意

- テストが通ったことは完成ではない。完成の条件を、画面で、利用者と同じ経路で確かめる。
- 長く動かすコマンド (ビルド、データの取得、ブラウザ) は、メモリと CPU に上限を掛けて流す。待つときは対象を特定できる条件で待つ (プロセス名での待ち合わせは自分自身に一致することがある)。
- 地図データとタイルの帰属表示は、画面と README の両方に出す (geo-software-legal-check)。
