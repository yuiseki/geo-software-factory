# 地図に載せるデータの組み立て

地物の一覧 (名所、店舗、実績など) を、人間に頼らず組み立てるときの手順。どの出どころを使うかは geo-software-data で決める。ここでは、決めた出どころから、配る形式にするまでを扱う。

## 出典を固定する

- 取得するものを、ID で固定する (Wikidata の Q 番号、OpenStreetMap の要素の種類と番号、Wikimedia Commons のファイル名)。検索の結果をそのまま使うと、次に組み立てたときに中身が変わる。
- 固定した一覧を、元データとして TSV などの 1 件 1 行のファイルに置く。配る形式 (JSON など) は、そこからビルドで作る。生成したファイルも 1 件 1 行、並び順を固定にして、差分で何が変わったかを読めるようにする。
- 外部の API に何度も問い合わせない。取得した結果を手元に残し、組み立て直すときはそれを使う。公開の OpenStreetMap のサーバーなど、利用の方針で大量の取得を禁じているところには、自前の写しか許された経路を使う。

## 行ごとに出典を持たせる

- 各行に、その位置や名前がどこから来たかの列を持たせる (`wikidata:Q194155`、`osm:node/1`、`photo:<ID>` など)。後で位置を直すとき、何を正本にしていたかが分かる。
- 写真やアイコンには、作者とライセンスを行ごとに持たせ、画面にも出す。
- 組み立ての検査で、出典、ライセンス、帰属表示が欠けた行があればビルドを落とす。例: 「image without credit or licence: <ID>」で止める。

## 正本を決める

同じ地物の位置が複数の出どころで食い違うことがある。どれを正本にするかを決め、データと README に書く。

- 決め方の例: 本人が現地で撮った写真の位置情報 (EXIF の GPS) があればそれを正本にし、無ければ Wikidata や OpenStreetMap の代表点を使う。
- 正本の順番は人間の価値判断を含むので、昼に決める。夜に食い違いを見つけたら、判断の方針に従って決め、「夜に決めたこと」に書く。
- 代表点しか無い地物 (付近、エリア) は、そうと分かる名前や印を付ける。

## 画像で照合するとき

写真と地物を結び付けるような、人の目に頼りたくなる照合は、候補を絞る仕組みと、目で見る仕組みに分ける。

- 写真を探すときは、写真だけに絞る。画像の置き場の「EXIF を持つ」の条件では、写真でない画像 (スクリーンショット、図) まで当たることがある。位置情報を持つものに絞る条件 (Gyazo なら `has:location`) の方が、撮った写真に近い。
- 候補を絞る: 位置 (撮影地点からの距離)、時刻、埋め込みモデルでの類似度で候補を並べる。
- 目で見る: 候補をまとめた一覧の画像 (コンタクトシート) を作り、エージェント自身が見て決める。
- 決めた結果は行ごとに出典として残す (`photo:<ID>`)。

## 配る前に機械で確かめる

地図に載せる GeoJSON を作ったら、geo-software-eval の [geocheck.py](../../geo-software-eval/scripts/geocheck.py) に、対象の範囲と必ず要る属性 (出典の列を含む) を渡して確かめる。テストに組み込んで、データを作り直すたびに流す。見た目では、緯度と経度の取り違えや投影座標の混入は気づきにくい。
