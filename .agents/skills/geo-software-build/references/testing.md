# テストの置き場所と確かめ方

## 本番と同じ実行環境でテストする

サーバーのテストは、本番と同じ実行環境で、本物の DB に対して流す。モックの DB では、SQL の誤りやマイグレーションの抜けが見えない。

- Cloudflare Workers なら、`@cloudflare/vitest-plugin` で手元の workerd の上でテストを動かし、設定で `readD1Migrations` を使ってマイグレーションを読み、テストの準備のファイルで `applyD1Migrations` を呼んで D1 へ当てる。Worker 全体に要求を送るテスト (`SELF.fetch`) と、バインディングを直接使うテスト (`env.DB`) の両方を書ける (https://developers.cloudflare.com/workers/testing/vitest-integration/)。
- 画面の部品のテストと Worker のテストは、同じテストの道具の別のプロジェクトに分ける (画面は Node、Worker は workerd)。
- ブラウザの API (IndexedDB など) を使う部品は、代わりの実装 (`fake-indexeddb` など) で Node の上でテストする。
- テストの中で使う鍵は、テスト専用の値をその場で作る。本物の鍵をテストに書かない。

## 配線をテストする

画面の「いつ、どのトークンで、何を送るか」の配線は、純粋な関数とサーバーの間にあって、どちらのテストにも入らない。ここを無テストで出すと、本番で壊れる (端末間で設定が同期されなかった、[pitfalls](pitfalls.md))。

- 配線を、依存 (通信、トークンの取得、時計) を差し込めるモジュールに切り出す。
- 時間切れ (通信が返らない)、トークン待ち (認証 SDK の読み込みが遅い)、実行中の再要求 (同期の最中にもう一度同期を頼まれる) をテストに書く。
- 同期の状態 (送信待ちの件数、最後に成功した時刻、失敗) を画面に出す。古い版の画面を開いている端末を見分けられる。

## 利用者と同じ経路で通す

通しの確認を、利用者と違う認証の経路 (テスト用の合言葉など) で通すと、利用者の経路の不具合が見えない。

- 外部の認証 SDK は、代役のスクリプトをブラウザの通信の差し替え (Playwright の `route`) で配り、わざと数秒遅らせて読み込ませる。本物の SDK と同じ順番 (画面の起動が先、認証が後) を再現できる。
- 端末をまたぐ機能は、ブラウザの文脈を 2 つ作り、片方で書いてもう片方に反映されるかを確かめる。
- 通しの確認のスクリプトはリポジトリに置き、README に動かし方を書く。

## 画面を確かめる

- 画面はブラウザで開いて、スクリーンショットを撮って自分で見る。テストが通っても、画面が崩れていることがある。
- ヘッドレスのブラウザは、既定で WebGL2 を使えないことがある。地図のライブラリは WebGL2 が無いと初期化に失敗し、アプリによっては別の原因のエラーに見える。Chromium なら `--use-angle=swiftshader --enable-unsafe-swiftshader --ignore-gpu-blocklist` でソフトウェアの WebGL を使う。SSH の X 転送の `DISPLAY` が残っていると WebGL が固まることがあるので外して起動する。
- 動画やライブ配信を含む画面は、通信が止まらないので「通信が落ち着くまで待つ」が終わらない。ページの読み込みを待ってから一定時間待つ。
- 写すものが時間で変わる画面 (ライブカメラ、動く地図) は、撮った画像の領域ごとの明るさを測り、条件を満たすまで待つか再読み込みする。
- 数で言えるもの (地図のタブを押せたか、マーカーの数、コンソールのエラー) は、ページの中を調べて自動で判定する。
