# レガシー GIS・CAD・登記データの取り込みと変換

業務用・自治体向け開発では、クラウドネイティブな GeoJSON や FlatGeobuf ではなく、庁内・社内台帳の Shapefile、CAD 図面、登記所備付地図、住所文字列がそのまま持ち込まれることが多い。典型的な罠と変換手順をまとめる。

## 1. Shapefile (`.shp` / `.dbf` / `.shx` / `.prj`) の罠

| 罠 | 症状 | 対処 |
|---|---|---|
| **文字コード (CP932 / Shift_JIS)** | UTF-8 として読むと施設名や住所が文字化けする | `.cpg` の有無に頼らず、`ogr2ogr` で `SHAPE_ENCODING=CP932` を明示して UTF-8 の GeoPackage / FlatGeobuf / GeoJSON へ変換する |
| **属性名 10 バイト制限** | 日本語カラム名や長いカラム名が途中で切れる | 元データの設計書・対応表を先に受け取り、変換時に正規の論理名へリネームする |
| **`.prj` 欠損・平面直角座標系** | 海上やアフリカ沖に飛ぶ、または緯度経度と X/Y が逆 | 地域の平面直角座標系 (EPSG:6669-6687) を確認し、`pyproj` / `ogr2ogr -s_srs` で明示指定して EPSG:4326 へ変換する |
| **2 GB 上限とマルチパート混在** | 巨大ファイルが欠損する、ポリゴンと穴の向きが壊れる | 受け取り直後に GeoPackage (`GPKG`) または GeoParquet へ変換し、`ST_MakeValid` 等でジオメトリを検証する |

## 2. CAD データ (`DXF` / `DWG` / `SXF`) の扱い

- **座標系を持たないローカル図面**: 建築・土木 CAD の多くは紙面座標や現場独自原点 (0, 0) で描かれており、そのまま地図に載らない。公共座標 (平面直角座標系) に乗っているか、または基準点 2 点以上によるアフィン変換 (ジオリファレンス) が必要かを最初に確かめる。
- **閉じていないポリゴンとブロック参照**: CAD の区画線は見た目が閉じていても線分 (`LINE`) の集合であることが多い。`ogr2ogr` / `ezdxf` / `QGIS` 等でポリゴン化 (polygonize) とブロック展開を行い、レイヤ名ごとに属性へ落とす。
- **DWG のライセンス・ツール制約**: DWG はプロプライエタリ形式のため、OSS ライブラリ (LibreDWG は GPLv3) のライセンス混入に注意する。発注者側で **DXF** または **SXF (P21/SFC)** へ書き出してもらうか、ODA File Converter 等を変換工程に分離する。

## 3. 登記所備付地図 (地図 XML)・公図・地番データ

- **任意座標系 (地図 XML の「座標系」区分)**: 法務局の登記所備付地図 XML には公共座標系のものと「任意座標系 (地図上のローカル座標)」が混在する。任意座標系はそのまま緯度経度へ変換できないため、別レイヤとして扱うか、道路・筆界の基準点で幾何補正する前提を設計に織り込む。
- **地番と住居表示の違い**: 住民が入力する「住居表示 (例: 〇〇一丁目2番3号)」と、土地台帳・登記の「地番 (例: 〇〇一丁目123番4)」は一致しない。検索要件に地番が含まれる場合は、法務局登記所備付地図や自治体保有の住居表示-地番対照表、または商用 API (`geo-software-infra`) の利用可否を確認する。

## 4. 住所・台帳 CSV の名寄せ前処理

- 庁内 CSV は「全角・半角の混在」「漢数字 (一丁目 vs 1丁目)」「『大字』『字』の省略」「ビル名・部屋番号の混入」「旧市町村名」を多く含む。
- ジオコーディング前に正規化パイプライン (NFKC 正規化、丁目・番・号の標準化、建物名分離) を通し、**一致しなかった行を「未マッチ一覧」として担当者へ返し修正できる運用** を組む。
