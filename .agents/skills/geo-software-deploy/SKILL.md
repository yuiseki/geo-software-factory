# geo-software-deploy

geo-software-build で完成の条件を満たしたものを、本番に出して確かめる。何をどこに置くかは geo-software-arch で決まっている。ここでは、昼に与えられた権限の範囲で出し、本番の URL で完成の条件を確かめ直すところまでを行う。

| reference | 読むとき | 中身 |
|---|---|---|
| [preflight](references/preflight.md) | 夜に入る前 (昼の準備) と、デプロイの直前 | 人間に先回りして頼むもの、値を出さずに確かめる方法 |
| [cloudflare-workers](references/cloudflare-workers.md) | Cloudflare Workers と D1 に出すとき | マイグレーション、デプロイ、独自ドメイン、確かめ方、実際に踏んだ挙動 |
| [cloud-deploy](references/cloud-deploy.md) | AWS、Google Cloud、Microsoft Azure、Vercel、Netlify、Render に出すとき | CLI 認証、プレビュー先行デプロイ、ロールバック、台帳記録の比較と共通手順 |
| [airgap-onprem](references/airgap-onprem.md) | LGWAN・閉域網・オンプレ VM/IIS へ納品するとき | 外部通信ゼロ確認、イメージ/wheel/タイル同梱バンドル、IIS/systemd 配備要点 |
| [verify](references/verify.md) | デプロイの後 | 本番の URL での確かめ方 |
| [scripts/deploy_gate.py](scripts/deploy_gate.py) | デプロイの直前とロールバックのとき | 未コミットの変更、評価した版との不一致、公開を止める監査指摘、破壊的な SQL をプログラムで拒み、出した版とコミットを対で台帳に記録して前の版を返す |
| [scripts/smoke.py](scripts/smoke.py) | デプロイの直後に | 本番の URL に GET だけで当て、疎通、状態コード、応答時間、`.git` や `.env` の露出、セキュリティのヘッダ、source map を判定する |
| [publish-repo](references/publish-repo.md) | リポジトリを公開するとき | 公開前の履歴の点検、公開するブランチ、説明文 |

## 入力

- geo-software-build の出力: テスト、型検査、ビルドが通るリポジトリと、完成の条件の達成状況。
- プロダクト概要の「準備したもの」: 認証済みの CLI、アカウント、鍵の名前、権限の範囲 (デプロイしてよい先、してはいけない操作、金額の上限)、公開の範囲。
- 権限の範囲が書かれていなければ、昼なら [preflight](references/preflight.md) の一覧で頼み、夜なら本番には出さず、下の「拒まれたとき」の方法で残す。

## 進め方

1. 直前の確認: テスト、型検査、ビルドを通す。CLI が認証済みであること、使う鍵が設定されていることを、値を表示せずに確かめる ([preflight](references/preflight.md))。出す版が、評価者が最後に合格とした版と同じかを確かめる。合格のあとに変更を加えていたら、評価をやり直してから出す。
2. DB のマイグレーション: 追加だけのもの (表や列を足す) は権限の範囲で当てる。消すもの、書き換えるもの (DROP、データの削除、型の変更) は取り消せないので、昼に承認を得ていなければ当てず、朝の報告に回す。
3. デプロイ: 提供元の手順で出す ([cloudflare-workers](references/cloudflare-workers.md))。出た版の ID を記録する。
4. 本番で確かめる ([verify](references/verify.md)): まず [scripts/smoke.py](scripts/smoke.py) を当て、落ちたら前の版に戻してから直す。続けて、API と静的ファイルを取得し、geo-software-eval の評価者に、同じシナリオを本番の URL で動かしてもらう。代役で評価していた外部のサービスは、ここで本物で確かめる。デプロイの直後の数秒は古い版が返ることがあるので、少し待って確かめ直す。
5. 独自ドメインの割り当てや、認証の許可するオリジンの追加は、[cloudflare-workers](references/cloudflare-workers.md) の注意に従う。以前の URL を使っている端末 (ホーム画面に入れた PWA など) を壊さない。
6. リポジトリを公開する場合は、公開の範囲が昼に合意されていることを確かめ、[publish-repo](references/publish-repo.md) の点検をしてから出す。
7. プロダクト概要に、出した URL、版の ID、確かめたこと、止めたことを書き、朝の報告にする。

## 拒まれたとき

デプロイやマイグレーションが、許可の検査 (自動の許可の分類器など) に拒まれることがある。夜は朝の人間の承認を待たず、承認の要らない範囲と方法で成果物を残す。拒まれた操作を、言い換えや分割で検査をすり抜けさせて通そうとはしない。

- 本番に流さない版を作る (Workers なら版のアップロードだけを行い、本番の割り当ては変えない)。
- 手元でビルドと検証を済ませ、作業ブランチにコミットする。
- 出すためのコマンドと順番を、朝の報告に書く。人間はそれを流すか、恒久的な許可を与えるかを選べる。
- 拒まれたことは「止まったこと」に書き、次の昼に、恒久的な許可 (例: 「この提供元への本番デプロイは確認なしでよい」) をもらうかを聞く。

## 出力

- 本番の URL と版の ID、確かめた結果 (完成の条件ごとに、満たしたかどうか)、スクリーンショット。
- プロダクト概要の更新: 「技術選定の結果」のデプロイの節、「止まったこと」(拒まれた操作、承認待ちのマイグレーション)。

## 注意

- 秘密の値はコマンドの出力にも報告にも出さない。人間が値を見る必要があるときは、人間が自分の端末で表示するコマンドを渡す。
- 取り消せない操作 (DB の削除、公開範囲の拡大、課金の増加、リポジトリの公開) は、昼に与えられた権限の範囲でだけ行う。
- 公開の後の運用 (鍵の制限、利用量と予算、障害への備え) は geo-software-ops に渡す。
