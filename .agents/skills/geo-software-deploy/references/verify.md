# 本番の URL で確かめる

デプロイが成功したことは、本番で動くことを意味しない。完成の条件を、本番の URL で確かめ直す。

## 順番

0. 機械で先に確かめる: [scripts/smoke.py](../scripts/smoke.py) を本番の URL に当てる。GET だけで、自分のサービスの外には出ない。`python3 smoke.py https://example.com --expect /api/places=200 --max-ms 3000` のように、主な API の状態コードと応答時間の上限を渡す。届かない、状態コードが違う、遅い、`.git` や `.env` がそのまま配られている、は不合格。セキュリティのヘッダ (HSTS、CSP、nosniff) の欠けと、画面のスクリプトの source map の公開は警告として報告に載せ、昼に決めた方針で扱う。帰属表示のように地図のライブラリが画面で描くものは、HTML の本文に現れないので、ここではなく下のブラウザで確かめる。
1. API: 主な読み出しの API を `curl` で取り、状態コードと中身の形を確かめる。認証が要る API は、認証なしで拒まれること (401 や 403) も確かめる。
2. 静的ファイル: トップページと、画面の URL (直接開いたときの SPA の振る舞い)、データのファイルを取得する。
3. 非公開のもの: 公開してはいけないデータが、認証なしの読み出しに含まれないことを確かめる。画面で隠しているだけになっていないか。
4. ブラウザ: 本番の URL に対して、geo-software-eval の評価者がシナリオを動かす (実装者が自分で確かめて終わりにしない)。コンソールのエラーとネットワークの失敗を記録する。地図は WebGL が要るので、ヘッドレスなら WebGL を有効にする (geo-software-build の testing)。
5. スクリーンショット: 撮って自分の目で見る。README に載せるものは、写したい状態 (全部のパネルに映像が出ている、など) になるまで待つか再読み込みする。
6. 端末をまたぐもの: 本番でも、ブラウザの文脈を 2 つ作って、片方の書き込みがもう片方に届くかを確かめる。

## 古い版を見ていないか

- デプロイの直後は、古い版や 404 が返ることがある。数秒待って確かめ直す。
- Service Worker を使う PWA は、端末に古い画面が残る。画面に版や同期の状態を出しておくと、古い版を開いている端末を見分けられる。データの取得はネットワークを先にし、失敗したときだけキャッシュを使う。

## 報告に書くこと

- 本番の URL と版の ID。
- 確かめたことと結果 (完成の条件ごと)。確かめられなかったことは、確かめられなかったと書く。
- スクリーンショットの置き場所。

## 戻す

本番で確かめて落ちたら、直す前に、まず利用者に届いている版を戻す。直すのはそのあとでよい。

- Cloudflare Workers は `wrangler rollback [version-id]` で、前の版に戻せる (wrangler 4.160.0 で確かめた。2026-11-13)。戻るのはコードと設定で、D1 のマイグレーションやデータは戻らない。マイグレーションを当てた版を戻すときは、前の版のコードが新しいスキーマで動くかを先に確かめる。追加だけのマイグレーション (表や列を足す) にしておくと、戻しやすい。
- 戻す先の版の ID は、デプロイのたびに記録しておく (プロダクト概要の「デプロイ」の節)。
- 戻したことと理由を、朝の報告の「止まったこと」に書く。戻すことは、昼に与えられた権限 (本番へのデプロイ) の範囲の操作として扱う。
