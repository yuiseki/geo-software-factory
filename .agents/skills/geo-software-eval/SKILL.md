# geo-software-eval

ダークファクトリーの中心は、AI がコードを書くことではなく、ソフトウェアの正しさを人間のコードレビュー以外の方法で評価し、その結果で開発を進めることにある ([WHAT_IS_DARK_FACTORY.md](../../../WHAT_IS_DARK_FACTORY.md))。評価基準と検証の仕組みは不要にならず、むしろ人間が先に設計する必要が高まる。このスキルは、その評価の設計 (昼) と実行 (夜) を扱う。

## 評価の原則

1. 外から観測できる振る舞いで判定する。コードを読んで正しそうかを判断しない。画面、通信、保存されたデータ、本番の URL で確かめる。
2. 評価は実装から切り離す。シナリオは実装のリポジトリの外 (または実装者が書き換えない場所) に置き、実装者に本文を見せない。実装者に返すのは、どの振る舞いがどう違ったかという症状だけにする。テストを書き換えて通すこと、シナリオに合わせ込むことを防ぐ (機械学習のホールドアウトと同じ考え方)。
3. 評価者は実装者と別にする。別の文脈 (別のエージェント、別のセッション) で動かし、できれば別のモデルにする。同じ前提を持つ評価者は同じ誤りを見逃す。
4. 評価の基準は人間が昼に決める。何をもって利用者の役に立ったとするかは、価値の判断を含む。夜のエージェントは基準を足してよいが、緩めない。
5. 評価そのものを疑う。全部通ったら、まず評価が甘くないかを確かめる ([eval-of-eval](references/eval-of-eval.md))。
6. 証跡を残す。何を、いつ、どの版に対して、どう判定したかを残し、朝に人間が読めるようにする。評価が走ったことは評価者の自己申告でなく記録で確かめ、結果が無いものは未評価とする。
7. 判定は遅れて覆ることがある。合格したものも、時間を置いて別の場面で確かめ直し、逃げた不具合を数える ([progress](references/progress.md))。

## 進め方

### 昼: 評価を設計する

1. プロダクト概要の価値の芯と Must の機能から、利用者が達成したいことを並べる。1 つの達成したいことを 1 本のシナリオにする ([scenarios](references/scenarios.md))。
2. 各シナリオに、始まりの状態、利用者の操作、観測すること、合格の判定を書く。観測と判定は [map-observables](references/map-observables.md) から選び、機械で判定できる形を優先する。
3. 本人と一緒に確かめる。シナリオの一覧を見せ、価値の芯を表しているか、抜けている場面がないかを、選択肢で聞く。ここが人間の主な仕事になる。
4. 見た目の基準 (参考の画面、余白、色) は、言葉だけでなく画像や数値でもらう。言葉だけの見た目の基準は読み違えやすい。
5. 外部のサービスに頼るシナリオは、代役で動かすか本物で動かすかを決める ([twins](references/twins.md))。本物でしか確かめられないものは、本番の確認に回す。
6. シナリオを実装のリポジトリの外に置き、置き場所をプロダクト概要の「完成の条件」に書く。

### 夜: 評価を動かす

1. 実装者 (geo-software-build) とは別の評価者を立て、シナリオを手元の版に対して動かす。
2. 判定する ([judging](references/judging.md))。機械で判定できるものは機械で、できないもの (見た目の妥当さ、文言の自然さ) は LLM の判定で、根拠の観測を添えて。
3. 落ちたシナリオは、症状 (どの画面で、何を期待し、何が観測されたか、スクリーンショット) だけを実装者に返す。シナリオの本文と判定の閾値は渡さない。
4. 実装者が直したら、全シナリオを動かし直す (直したところ以外が壊れていないか)。
5. 全部通ったら、[eval-of-eval](references/eval-of-eval.md) で評価が甘くないかを確かめる。
6. デプロイの後、同じシナリオを本番の URL に対して動かす (geo-software-deploy)。
7. 結果を [assets/eval-report-template.md](assets/eval-report-template.md) の形で残し、朝の報告に入れる。

## 出力

- 昼: シナリオの一式 (置き場所)、判定の方法、代役の方針。プロダクト概要の「完成の条件」に置き場所と要約。
- 夜: 評価の報告 (シナリオごとの合否と根拠、評価の評価の結果、証跡の置き場所)。

## 注意

- 評価が通ったことは、正しさや安全性の証明ではない。確かめた範囲を書き、確かめていない範囲 (未確認の端末、本物でしか分からない外部サービス、法令) を書く。
- 評価者に本番の書き込みや削除をさせない。本番での評価は読み出しと、評価用に分けたアカウントやデータの範囲で行う。
- 評価のためのコストを見込む。シナリオの数 × 動かす回数 × (ブラウザ、LLM の判定) の費用と時間を、判断の方針の上限に収める。
