# 別の文脈による設計レビュー

設計の下書きを、相談の経緯を知らない読み手に確かめてもらう。会話を重ねた作成者が、本人の意図や既存の制約を暗黙の前提にしてしまうことを減らす。Google の [Elephant-Goldfish Model](https://github.com/google/elephant-goldfish-model) の考え方を、プロダクト概要と独立評価を使うこのリポジトリの流れに合わせたもの (参照: 2026-11-14)。

## いつ使うか

実装前に、設計上の選択が後戻りしにくい場合や、認証、公開、地図データの権利、費用、外部サービスとの境界など、見落としの影響が大きい場合に使う。小さな文言修正や、設計上の選択を伴わない変更に、同じ工程を必須にしない。本人がレビューを指定したときは、その範囲と依頼に従う。

- **設計者 (Elephant)**: 本人との会話、プロダクト概要、既存の制約を読み、設計案と判断理由を書く。
- **設計レビュー者 (Goldfish)**: 会話履歴を引き継がない別の文脈で、設計案と、明示的に指定された根拠資料を読む。記録されていない前提、矛盾、実装や運用のリスクを探す。
- **振る舞いの評価者**: [judging](judging.md) に従い、実装のコードを読まず、別に管理されたシナリオで外から判定する。設計レビュー者とは役割も渡す情報も異なる。

設計レビューは、実装後の評価やテストの代わりにはならない。設計レビュー者が既存コードを根拠として読むことはできるが、振る舞いの評価者には読ませない。実装者に見せない評価シナリオや閾値は、設計レビューの資料や指摘に混ぜず、評価の隔離を保つ。

## 進め方

1. 設計者は、プロダクト概要と必要な設計案をファイルにまとめる。価値と利用場面、範囲、選択肢と選んだ理由、データの出どころ、外部サービスと権限の境界、障害時の振る舞い、未決定事項、根拠へのリンクを含める。情報が足りなければ未定と書く。
2. レビュー対象のファイル、版 (コミットや内容のハッシュ)、目的、観点、参照してよい資料を指定する。会話の要約や設計者の結論を追加の指示として渡さない。必要な情報は先に設計案に書く。秘密、私的な情報、実装者に見せない評価シナリオを資料に含めない。
3. 利用環境と許可の範囲で、会話履歴を受け継がない別のエージェントやセッションを使う。レビュー者には設計案と指定資料を読ませる。仕様、根拠、既存コードが食い違う場合は、それぞれの箇所を挙げてもらう。参照資料を渡せない場合は、何が未確認かを残す。
4. 観点を選んで確かめる: 目的に対して複雑すぎないか、初見で理解できるか、設計の抜けや失敗時の扱いはないか、既存コードと両立するか、実装できる具体性と確かめ方があるか。地図では縮尺と対象範囲、地物の形、データの鮮度、帰属表示、端末や通信の制約も対象にする。必要に応じて観点ごとに読み手を分ける。
5. 指摘には、対象の箇所、根拠、起こりうる影響、重要度、未確認事項を付ける。重複をまとめ、設計者が「修正」「見送り (理由)」「判断待ち」に仕分ける。本人にしか決められない価値やトレードオフ、権限の範囲外の変更は本人に戻す。夜は事前に決めた判断の方針と権限の範囲で進め、決められないものを朝に報告する。
6. 採用した指摘を設計案に反映し、必要な箇所を新しい版に対してもう一度確かめる。レビュー対象の版、レビュー者の分離方法、使った資料、指摘と判断、未確認・未実施の観点を記録し、概要の「設計レビュー」に置き場所を書く。作成者だけで見直した場合は自己確認と記し、独立レビュー済みとしない。

独立した文脈を用意できない、レビュー者が失敗した、または結果が返らなかった場合は、その観点を「未実施」とする。ゼロ件の指摘や合格として扱わない。自己確認で進める場合も独立したレビューと区別し、残るリスクと未実施を報告する。公開やマージに別途決められた関門は省かない。

## 設計と実装のずれ

設計と実装の両方が存在するときは、対象の版を明記して、設計に書いた範囲、データの出どころ、境界、障害時の振る舞いと、実際のコードや観測を照合する。差分は「未実装」「実装が設計と異なる」「確認できない」などに分け、各々に設計と根拠の位置を付ける。設計が古いことも実装の不具合もありうるので、自動的にどちらかを正本にせず、本人の意図と判断の方針に沿って扱う。評価シナリオと閾値の変更は、[brakes](brakes.md) の承認を経る。
