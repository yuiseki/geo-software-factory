# 評価そのものを確かめる

評価の仕組みがあることは、正しく評価されていることを保証しない。広く使われている評価のデータでさえ、要求の書き漏れ、厳しすぎる判定、確かめる範囲の不足が見つかっている ([WHAT_IS_DARK_FACTORY.md](../../../../WHAT_IS_DARK_FACTORY.md) の「評価基準そのものの誤り」)。全部通ったら、まず評価を疑う。

## 壊した版で落ちるか

- 評価を作ったら、わざと壊した版を用意して、評価が落ちることを確かめる。例:
  - 地図を描かない (地図の初期化を止める)。
  - 地物を 1 件も出さない、または全部出す (絞り込みを無効にする)。
  - 帰属表示を消す。
  - 書き込みを保存しない、別の端末に届けない。
  - 非公開のデータを認証なしの読み出しに含める。
- 壊した版で通ってしまうシナリオは、判定が甘い。観測を足すか、判定を厳しくする。
- 壊し方の一覧と、それぞれでどのシナリオが落ちたかを、評価の報告に残す。

## 甘い判定の見つけ方

- 「エラーが出ないこと」「要素があること」だけの判定は、何もしない実装でも通る。期待する中身 (件数、文言、状態) まで判定しているかを見る。
- LLM の判定の根拠が、渡した観測に無いことを言っていないかを見る。
- 一度も落ちたことのないシナリオは、壊した版で試す。

## 厳しすぎる判定の見つけ方

- 利用者にとって正しいのに落ちる判定 (内部の文言や、版で変わる細部に合わせた判定) は、作り直しのたびに偽の不合格を出し、実装者を誤った方向へ動かす。
- 同じシナリオが、症状を直しても落ち続けるときは、シナリオの側を疑う。夜は判定を緩めず、朝の報告に「シナリオの見直しの候補」として書き、昼に人間と直す。

## 抜けを見つける

- 朝の報告で、人間が実際に使って気づいた不具合を、どのシナリオが捕まえるべきだったかに対応づける。捕まえるシナリオが無ければ、次の昼に足す。
- 本番の不具合の報告 (利用者の声、エラーの記録) も同じように対応づける。
- 評価の改善は、評価に使ったものと別の事例で効果を確かめる。落ちた事例に合わせて直した評価で、同じ事例を測っても改善は言えない。
