# 実装者と評価者を、別のコンテナに分ける

評価の原則の「評価は実装から切り離す」を、エージェントの心がけでも、道具の拒否の規則でもなく、ファイルシステムで守る。拒否の規則は事故の防止にしかならない。Claude Code で試すと、絶対パスを `/` 1 つで書いた規則は何にも当たらず、`//` で書いても、許可した `python3` からは読めた (2026-11-13、[judging](judging.md))。実装者の側にシナリオが無ければ、どの道具でも読めない。

## 形

ひな形は [assets/isolation/compose.yaml](../assets/isolation/compose.yaml)。どのパスも、ホストの絶対パスを環境変数で渡す。

| ディレクトリ | 実装者のコンテナ | 評価者のコンテナ |
|---|---|---|
| 実装のリポジトリ (`APP_DIR`) | 読み書き | 載せない |
| 依頼 (`HANDOFF_DIR`) | 読み書き | 読むだけ |
| 症状 (`FEEDBACK_DIR`) | 読むだけ | 読み書き |
| シナリオ (`SCENARIOS_DIR`) | 載せない | 読むだけ |
| 報告 (`REPORT_DIR`) | 載せない | 読み書き |
| 評価の道具 (`EVAL_SCRIPTS`、このスキルの scripts) | 載せない | 読むだけ |

- 評価者は実装のコードを持たない ([judging](judging.md) の「評価者に実装のコードを読ませない」)。判定する版は、実装者の依頼から受け取る。
- どちらのコンテナも、権限 (capability) を全部外し、権限の昇格を禁じ、CPU、メモリ、プロセスの数に上限を掛ける。Docker のソケットはどちらにも載せない。載せると、コンテナから別のコンテナを立てて、何でも読める。
- 評価者のコンテナは、ルートのファイルシステムを読むだけにする。

## 受け渡し

1. 実装者は、アプリを自分のコンテナで起動し、`/work/handoff/ready.json` に `{"rev": "<コミット>", "port": 8787}` を書く。同じ版をもう一度評価してほしいときは `"nonce"` を足す。
2. 評価者は [scripts/eval_watch.py](../scripts/eval_watch.py) で依頼を待ち、`http://implementer:<port>` を [scripts/run_eval.py](../scripts/run_eval.py) で判定する。宛先のホストは評価者が決め、依頼のほかの項目は無視する。実装者に評価者の向け先を変えさせない。形の違う依頼には、評価せずに、その旨を症状に書く。
3. 症状は `FEEDBACK_DIR/eval-feedback.md` に書かれる。実装者の側では、geo-software-swarm の [hooks.py](../../geo-software-swarm/scripts/hooks.py) の deliver に `EVAL_FEEDBACK=/work/feedback/eval-feedback.md` を渡し、道具の呼び出しのたびに届ける。
4. 報告 (閾値と全部の出力を含む) は `REPORT_DIR` に残り、朝に人間が読む。

実装者のエージェント (Claude Code、Codex など) は、実装者のコンテナの中で動かす。ホストで動かすと、ホストにあるシナリオを読めるので、分けた意味がなくなる。エージェントの認証の状態は、実行専用の場所 (evals の `run_codex_docker.sh` と同じく、普段の設定のディレクトリではないもの) から載せる。

## 夜の前に、試して確かめる

[scripts/check_isolation.py](../scripts/check_isolation.py) を、夜と同じ環境変数と compose のファイルで動かす。

- シナリオと報告のディレクトリに、毎回新しい無作為の目印を書き、実装者のコンテナの中で、ファイルシステム全体と環境変数を探す。見つかったら隔離は崩れている。
- 同じ探し方で、評価者の側から目印が見つかることを確かめる。見つからないなら探し方が効いておらず、実装者の側の「見つからない」は何も示さない。
- 実装者が症状を書き換えられないこと、依頼を書けること、Docker のソケットが無いこと、評価者がシナリオを書き換えられないことを確かめる。
- 「書けない」「無い」を確かめる項目は、コンテナが起動に失敗しても失敗の終了コードを返すので、通ったように見える。各項目は、コンテナの中で動いた印が出力にあるときだけ数える。この仕組みを入れる前の版では、ネットワークを作れずにコンテナが 1 つも起動しなかったのに、4 項目が通っていた。
- 目印は終わったら消し、作ったネットワークも片づける。

わざと壊した構成 (実装者にシナリオを載せた compose) で落ちることも、このスキルの試験 (`GSF_DOCKER_TESTS=1`) で確かめている。

## 環境の落とし穴

- Docker の既定のアドレスの範囲を使い切ったホストでは、ネットワークを作れない (`all predefined address pools have been fully subnetted`)。他のプロジェクトのネットワークを消さずに、空いている範囲を上書きのファイルで指定し、夜も確かめも同じファイルの組で動かす。

```yaml
networks:
  night:
    ipam:
      config:
        - subnet: 10.213.57.0/24   # ip route と docker network inspect で空きを確かめてから
```

- ブラウザのシナリオ (command の確かめで Playwright を動かすもの) は、評価者のイメージに Playwright とブラウザを入れる (`EVALUATOR_IMAGE`)。実装者のイメージには入れなくてよい。
