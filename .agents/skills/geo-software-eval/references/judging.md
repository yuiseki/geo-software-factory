# 判定の仕方

## 機械の判定を先に

- 数、状態コード、文言の有無、範囲の包含のように機械で決まるものは、機械で判定する。LLM に判定させない。
- 閾値は昼に本人と決めた値を使う。夜に閾値を緩めない。

## LLM の判定

見た目の妥当さ、文言の自然さ、利用者の目的を果たしたと言えるか、のような機械で決めにくいものは、LLM に判定させる (LLM-as-a-Judge)。

- 判定の観点をシナリオに書いておき、その観点だけで判定させる。「良いか」とだけ聞かない。
- 根拠の観測 (スクリーンショット、DOM の抜粋、ネットワークのログ) を渡し、判定と一緒に、どの観測を根拠にしたかを返させる。根拠の無い合格は不合格として扱う。
- 合否だけでなく、確信の度合いを返させる。確信の低い判定は、朝の報告で人間に見てもらう候補にする。
- 同じ観測で複数回判定させ、割れたら不合格の側に倒す。
- 複数のシナリオの結果をまとめた「どれだけ利用者の意図を満たしたか」(StrongDM の Satisfaction のような割合) は、進み具合の目安として使う。高いことだけで正しさの証明にはしない。

## 評価者の独立

- 評価者は、実装者と別の文脈で動かす (別のエージェント、別のセッション)。実装の会話の履歴を評価者に渡さない。
- できれば、実装者と別のモデル (別の提供元、別の系列) で判定する。同じモデルは同じ誤りを見逃しやすい。
- 評価者に実装のコードを読ませない。読むと「こう作ったからこう動くはず」という判定になる。

## 実装への返し方

- 落ちたシナリオについて、症状だけを返す: どの画面で、どの操作のあと、何を期待し、何が観測されたか。スクリーンショットとログを添える。
- シナリオの本文、判定の閾値、他のシナリオの存在は返さない。
- 同じ症状が何度も返るときは、症状の書き方が実装者に伝わっていないか、シナリオの側が誤っているかを疑う ([eval-of-eval](eval-of-eval.md))。

## 判定が割れる、決められないとき

- 夜は人間を待たない。判断の方針に従って不合格の側に倒し、理由を「夜に決めたこと」に書く。
- 朝の報告に、判定が割れたシナリオと根拠の観測を並べ、人間に見てもらう。人間の判定は次の昼にシナリオか閾値の改善に反映する。
