# 判定の仕方

## 機械の判定を先に

- 数、状態コード、文言の有無、範囲の包含のように機械で決まるものは、機械で判定する。LLM に判定させない。
- 閾値は昼に本人と決めた値を使う。夜に閾値を緩めない。

## LLM の判定

見た目の妥当さ、文言の自然さ、利用者の目的を果たしたと言えるか、のような機械で決めにくいものは、LLM に判定させる (LLM-as-a-Judge)。

- 判定の観点をシナリオに書いておき、その観点だけで判定させる。「良いか」とだけ聞かない。
- 根拠の観測 (スクリーンショット、DOM の抜粋、ネットワークのログ) を渡し、判定と一緒に、どの観測を根拠にしたかを返させる。根拠の無い合格は不合格として扱う。
- 合否だけでなく、確信の度合いを返させる。確信の低い判定は、朝の報告で人間に見てもらう候補にする。
- 同じ観測で複数回判定させ、割れたら不合格の側に倒す。
- 複数のシナリオの結果をまとめた「どれだけ利用者の意図を満たしたか」(StrongDM の Satisfaction のような割合) は、進み具合の目安として使う。高いことだけで正しさの証明にはしない。

## 評価者の独立

- 評価者は、実装者と別の文脈で動かす (別のエージェント、別のセッション)。実装の会話の履歴を評価者に渡さない。
- できれば、実装者と別のモデル (別の提供元、別の系列) で判定する。同じモデルは同じ誤りを見逃しやすい。
- 仕組みで分ける: [scripts/run_eval.py](../scripts/run_eval.py) は、シナリオと報告が実装のリポジトリの中にあれば動かず、実装者への返し (`eval-feedback.md`) には、判定した版、シナリオごとに人間が昼に書いた症状の 1 行、要求した道筋と観測 (状態、地物の数、検出の種類) だけを書く。ブラウザのシナリオは command の確かめにし、`OBSERVED:` で始まる行だけが実装者に届く。実装者の設定では、シナリオの置き場所の読み出しを拒否に入れ (geo-software-swarm の [設定のひな形](../../geo-software-swarm/assets/unattended-settings.json))、症状はフックで届ける。ただし、拒否の規則は事故の防止で、隔離ではない。2026-11-13 に Claude Code で試したところ、絶対パスを `/` 1 つで書いた規則は何にも当たらず、ファイルを読めてしまった (`//` で始めると絶対パスになり、Read の道具と `cat` は拒まれた)。許可した `python3` からは読めた。隔離するなら、実装者と評価者を別のコンテナで動かし、実装者の側にシナリオを置かない ([isolation](isolation.md))。どの方法でも、試しに読ませて拒まれることを確かめてから夜に入る (AGENTS.md の統治の層の「権限の検証」)。
- 評価者に実装のコードを読ませない。読むと「こう作ったからこう動くはず」という判定になる。
- 夜に入る前に、評価者が使えることを確かめる (別のモデルに届くか、使用量の上限に余裕があるか、判定に足りる能力のモデルか)。
- 夜の途中で評価者が使えなくなったら (上限、障害)、実装者自身や能力の足りないモデルに黙って代えない。そのシナリオは「未評価」とし、未評価の版は判断の方針に従ってプレビューまでに留める。代えたときは、代えたことを判定と一緒に書き、独立の評価には数えない。

## 評価が本当に走ったか

- 評価者の報告の文面ではなく、記録 (ブラウザの操作の記録、スクリーンショットの時刻、道具の呼び出しの記録) で、シナリオが実際に動いたことを確かめる。記録の無い合格は、評価していないものとして扱う。
- 結果が無いことを、合格と扱わない。CI が走っていない、シナリオが飛ばされた、時間切れで終わったものは「未評価」と書く。
- 判定は版 (コミット、デプロイの版の ID) に結び付ける。最後の評価のあとに変更を加えたら、その判定は使えない。デプロイの前に、評価した版と出す版が同じかを確かめる。
- 不安定な失敗の再実行は 1 回までにし、再実行したことと理由を書く。繰り返し不安定なシナリオは、評価の側の不具合として [eval-of-eval](eval-of-eval.md) に回す。再実行を増やして隠さない。

## 実装への返し方

- 落ちたシナリオについて、症状だけを返す: どの画面で、どの操作のあと、何を期待し、何が観測されたか。スクリーンショットとログを添える。
- シナリオの本文、判定の閾値、他のシナリオの存在は返さない。
- 同じ症状が何度も返るときは、症状の書き方が実装者に伝わっていないか、シナリオの側が誤っているかを疑う ([eval-of-eval](eval-of-eval.md))。

## 判定が割れる、決められないとき

- 夜は人間を待たない。判断の方針に従って不合格の側に倒し、理由を「夜に決めたこと」に書く。
- 朝の報告に、判定が割れたシナリオと根拠の観測を並べ、人間に見てもらう。人間の判定は次の昼にシナリオか閾値の改善に反映する。
