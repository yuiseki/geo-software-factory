# 進み具合の測り方

固定された問題と固定された評価で測るベンチマークと違い、ソフトウェアファクトリーは、自分の仕事、自分の評価、測られる進み具合を自分で変える。Jiang と Lysenko (Instant Software Factories、arXiv:2610.36254) は、これを内生的なフィードバックと呼び、3 つの経路を挙げている。

| 経路 | 起きること | 論文の事例 | 守り方 |
|---|---|---|---|
| 仕事 | エージェントが自分で issue を立てて、仕事を増やす | 新しい issue の 95% をエージェントが立てた | 重さは人間が昼に決めた基準で付け、件数で測らない |
| 評価 | エージェントが CI や評価を書き換える | CI の変更の PR 58 件中 40 件がエージェント、7 件が検査を緩めた | 評価をエージェントが書き換えられない場所に置く (ホールドアウト) |
| 遅れた判定 | 独立の評価より先にマージされ、誤った修正が出荷される | 直したとされた 450 件中 25 件 (5.6%) が後で誤りと分かり、7 件はそのまま出荷された | 時間を置いてから測る |

マージ数や閉じた issue の数 (スループット) は、これらで水増しされる。進み具合は、次のすべてを満たす変更だけで数える。

1. 独立に価値づけされている: 重さと目的を、エージェントではなく、昼に人間が決めた基準で付けた。
2. 検証されている: エージェントが書き換えられない評価 (geo-software-eval のシナリオ) で確かめた。
3. 届いている: 本番に出て、利用者に届いた。
4. 持ちこたえている: 一定の確かめの期間 (例: 2 週間) のあと、逃げた不具合として見つかっていない。

## ぶれを先に測る

同じ版を測り直しても、結果はぶれる (同じコミットで測り直した 58 回の結果の幅が 21% あった例がある)。改善を言う前に、同じ版を何回か測り直してぶれの幅を出し、それを超えた差だけを改善として数える。1 回ずつの比較で結論を広げない。

## 逃げた不具合

- 「直した」とされたのに、同じ不具合の別の場面で壊れている、または一部が直っていないものを、逃げた不具合と呼ぶ。
- 見つける役割が、直したとされた issue を時間を置いて確かめ直す。見つけたら、元の issue を開き直すか、新しい issue に元の issue を書く。
- 逃げた不具合の率 (逃げた数 / 直したとされた数) を目的ごとに数える。見つかっていないことは、正しいことを意味しない。確かめの範囲を一緒に書く。

## 報告に書くこと

- 目的ごとの、届いて持ちこたえた変更の数 (重さで重みづけ)。
- 逃げた不具合の数と率、見つけた経路、出荷前に直せたか。
- 評価、CI、エージェントへの指示を変えた PR の一覧と、検査を緩めたものの有無。
- 費用 (LLM、CI、人間のレビューの時間) と、使用量の上限の残り。
- スループット (マージ数、issue 数) は参考として別に書き、進み具合と混ぜない。
