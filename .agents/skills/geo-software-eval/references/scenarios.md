# シナリオの書き方

シナリオは、利用者が達成したいことを 1 つ、外から観測できる形で書いたもの。単体テストが「関数が正しいか」を見るのに対し、シナリオは「利用者が目的を果たせたか」を見る。

## 1 本の中身

- 名前: 利用者が達成したいことを一文で (例: 旅先で、近くの未解除の名所を見つけて解除する)。
- 価値とのつながり: プロダクト概要のどの価値と Must を表すか。
- 始まりの状態: 端末 (画面の大きさ、タッチの有無)、ログインの有無、保存済みのデータ、現在地、通信の状態 (オフラインなど)。
- 操作: 利用者がすることを順に。画面の要素は、見た目の文言や役割で指す (内部の ID や関数の名前で指さない)。
- 観測: 各操作のあとに何を見るか ([map-observables](map-observables.md))。
- 合格の判定: 機械で判定できる条件を先に、LLM に判定させる条件を後に。LLM に判定させる条件には、判定の観点を書く。
- 対象: 手元の版、本番の URL、またはその両方。

ひな形は [assets/scenario-template.md](../assets/scenario-template.md)。

## 粒度と数

- 1 本で 1 つの達成したいこと。1 本に複数の目的を詰めると、落ちたときに何が壊れたか分からない。
- Must の機能ごとに少なくとも 1 本。価値の芯に関わるものは、場面を変えて複数本 (例: 旅行中と、振り返るとき)。
- 書けない人、初めて開いた人、オフライン、遅い通信、小さい画面のような、作る側が見落としやすい始まりの状態を混ぜる。
- 非公開のもの、権限の境界 (他人の記録を書き換えられないこと) を必ず入れる。

## 本人と決めること

シナリオの本文はエージェントが下書きしてよいが、次は本人に確かめる。

- このシナリオの一覧で、価値の芯が表されているか。足りない場面はないか。
- 合格の判定の閾値 (初回表示の時間、地物の数、許せる表示のずれ)。
- 見た目の基準 (参考の画面、色、余白)。言葉だけでは読み違えるので、画像か数値でもらう。
- 本物の外部サービスで確かめるシナリオと、代役で済ませるシナリオの分け方。

## 置き場所

- 実装のリポジトリの外に置く (例: 評価用の別リポジトリ、評価者だけが読む作業ディレクトリ)。同じリポジトリに置くなら、実装者が書き換えない取り決めをプロダクト概要に書き、変更の履歴で確かめる。
- 実装者に本文を見せない。見せると、シナリオの手順だけを通る実装になる。
- シナリオを変えるときは、理由を書いて残す。夜に変えてよいのは足すことだけで、緩めることはしない。

## 書いてはいけないもの

- 実装の内部に触れる手順 (関数を直接呼ぶ、DB を直接書き換える)。利用者の経路で到達できない状態は、始まりの状態として用意する。
- 実装の詳細に合わせた判定 (特定の CSS のクラス名、内部のイベント名)。作り直すと壊れ、利用者にとっての正しさを表さない。
- 「エラーが出ないこと」だけの判定。何も表示しない実装でも通る。
