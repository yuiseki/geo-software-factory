# 既存改修・依存関係マイグレーション・全面作り直しの進め方

地図サービスや SDK の乗り換えだけでなく、既存の地図ソフトウェアの改修・機能追加、古い依存関係のアップデート、レガシー構成 (jQuery / 古い PHP・Java・Python 2 / 旧 GIS サーバー) からモダン構成への全面作り直しも、この手順で進める。

## パターン別の基本方針

| 案件の種類 | 最初にやること | 切り替え・検証の要点 |
|---|---|---|
| **既存ソフトの改修・機能追加** | 既存コードを変えずに、影響範囲の特性テストを旧ソフト上で書いて通す | 「壊さない互換テスト」と「新機能のテスト」を分け、TDD で積む |
| **依存関係マイグレーション** | 現在の依存版を固定し、空間計算・描画・API 応答の特性テストを通す | 破壊的変更が大きい場合は中間版を挟み、各段で全テストを通す |
| **モダン構成への全面作り直し** | 旧ソフトを正本 (Oracle) として特性テストを確立し、新環境へ厳密に移植する | Strangler Fig で画面・API 単位に段階移行し、新旧突合 (Parity Check) で一致を証明する |

## 守るべき順番 (TDD と正本の原則)

1. **旧ソフトウェアを正本にする**: 既存のドキュメントが古くても、実際に動いている旧ソフトウェアの入出力を正本として扱う。
2. **テストが無ければ旧ソフトに先に書く**: テストが無いレガシーコードに直接手を入れない。まず [characterization-legacy](../../geo-software-tdd/references/characterization-legacy.md) に従って旧ソフト上に特性テストを追加し、全件通ることを確かめてコミットする。
3. **新環境に厳密に同じロジックのテストを書く**: 全面作り直しや別ライブラリへの移行では、旧ソフトで通った特性テストと同じ入力・同じ期待値・同じ境界条件のテストを新環境側に先に書く。
4. **TDD で実装し、新旧を突合する**: 新環境でテストを通したあと、同一入力を旧環境と新環境に流す突合チェック (座標誤差、件数、プロパティ型、エラー時の状態コード) を行い、差分が 0 件または合意済み仕様変更のみであることを確かめる。

## 地図特有の移行で壊れやすい箇所 (棚卸し対象)

- **座標軸と投影法**: `lon, lat` と `lat, lon` の順、旧日本測地系 (Tokyo Datum / EPSG:4301) と世界測地系 (JGD2011 / WGS84)、平面直角座標系の系番号、ズームレベル 0 のタイル原点の差。
- **スタイルの解釈と描画順**: Mapbox GL JS / MapLibre / OpenLayers / Leaflet の間で、ズームのオフセット (`tileSize` 256 vs 512)、フォント名、アイコンアンカー、重なり許容 (`text-allow-overlap`) がズレやすい。
- **空間演算ライブラリの丸めと境界**: PostGIS、GEOS/Shapely、Turf.js、JSTS でポリゴン境界上の点の内外判定や面積計算の端数処理が異なることがある。境界上のテストケースを特性テストに必ず含める。
- **ビルドと非推奨 API**: Webpack 4 / Node 12 / Python 2 等のレガシー資産を移す場合、ポリフィル (`Buffer`, `process`) や ESM/CJS 混在、WASM の MIME タイプ設定 (`application/wasm`) の抜けを確認する。
