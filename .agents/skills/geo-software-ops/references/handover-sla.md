# 受託・自治体納品後の引き渡し運用と SLA

自社サービスと違い、受託開発や自治体案件では「納品して終わり」ではなく、顧客アカウント環境やオンプレミス環境での継続運用、または別担当・別ベンダへの引き継ぎを前提に運用設計を残す。

## 1. SLA・RPO・RTO の定義表

昼の擦り合わせで決めた非機能要件を、検証可能な数値として運用設計書に残す。

| 項目 | 確認する内容 | 地図プロダクト特有の論点 |
|---|---|---|
| **稼働目標 (SLA)** | 営業時間内 (例: 平日 8:30-17:15) か 24/365 か | 外部タイル提供元障害時の「予備スタイル自動切替」が稼働率に効く |
| **目標復旧時点 (RPO)** | 何時間前までのデータに戻せればよいか | 編集系 GIS の PostGIS WAL アーカイブ / 日次ダンプ頻度を決める |
| **目標復旧時間 (RTO)** | 障害発生から何時間以内に復旧するか | 大容量 PMTiles (数十 GB) の再配置時間を考慮する |
| **計画停止ウィンドウ** | メンテナンスを許される曜日・時間帯 | 自治体窓口や防災業務では年度末・台風期の凍結期間を明記する |

## 2. バックアップと災害復旧 (DR)

- **正本 DB (PostGIS 等)**: 日次の論理ダンプ (`pg_dump -Fc`) に加え、RPO が 1 時間以下なら PITR (Point-in-Time Recovery) を有効にする。復元テストを年 1 回以上、別環境で実施する手順を残す。
- **タイル・静的アセット (PMTiles / スタイル / フォント)**: ソースデータと生成スクリプト (`tippecanoe` / `planetiler` の版とコマンド) を Git に残し、生成済みバイナリは別リージョンまたは別媒体へ複製する。
- **秘密情報・証明書**: API キーや TLS 証明書の有効期限台帳 (発行日、失効日、更新手順、担当者) を引き渡し物に含める。

## 3. 障害切り分けフロー (1 次対応向け)

引き継ぎ先が最初に見る切り分け表を用意する。

1. **地図背景だけ出ない (ピンや独自レイヤは出る)**: ベースマップ提供元の障害ページ、API キーの referrer/Origin 制限、無料枠・予算上限超過を疑う ([fallback](fallback.md))。
2. **独自レイヤだけ出ない**: バックエンド API / PostGIS / タイル配信サーバーの死活、CORS、証明書期限、DB 接続数上限を確認する。
3. **特定端末・庁内ネットワークだけ出ない**: プロキシ、TLS インスペクション、WebGL 無効環境、IP 制限、CDN ブロックを確認する。

## 4. 引き渡し文書一式 (チェックリスト)

- [ ] システム構成図 (ネットワーク境界、外部送信先、データの流れを含む)
- [ ] 環境変数・秘密鍵・外部契約の一覧 (値は書かず、管理場所と更新期限のみ記載)
- [ ] バックアップ取得・復元手順書 (実測した所要時間を記載)
- [ ] データ更新・タイル差し替え手順書 (検証から本番切替、ロールバックまで)
- [ ] 年間保守カレンダー (OS/ライブラリ脆弱性対応、SSL 証明書・API キー更新、地図データ年次更新)
