# geo-software-product-grilling

作りたい地図プロダクトを、本人への選択肢つきの質問を 1 問ずつ重ねて明確にし、プロダクト概要にまとめる。本人の頭の中の答えを当てにいくのではなく、エージェントが材料から選択肢を作り、本人が選ぶか書き換えることで、2 人で概要を形にしていく。

| reference | 読むとき | 中身 |
|---|---|---|
| [question-bank](references/question-bank.md) | 質問を組み立てるとき | 観点ごとの質問と選択肢の作り方、2026-11-10 の聞き取りの実例 |

ひな形は [assets/product-brief-template.md](assets/product-brief-template.md)。

## 目的

次がそろったら問い詰めを終え、プロダクト概要にまとめて確認をとる。

- 一行の説明: 誰の、どんな困りごとを、地図で何をすることで解くか
- 価値の順位: 届ける価値を、本人が重要な順に並べたもの (最重要、重要、副次的)
- 機能: Must / Should / Could。最初の版の期限があれば、その期限までの Must
- 後の段階の入口の条件 (リポジトリ直下の AGENTS.md の表): geo-software-arch の 4 項目 (要る機能、データの大きさと対象範囲、ルールの強制、対象端末) と、geo-software-infra の 3 項目 (利用形態、規模、対象地域)。分からない項目は「未定」と書けるが、推測では埋めない

## 進め方

1. 依頼と、本人が示した材料 (参考の URL、過去の記録、似たサービス) を読む。材料は質問と選択肢を作るためだけに使い、読んだ結果の要約や、エージェントの見立てを本人に先に見せない。見せると、本人が自分の答えではなく見立てに寄せてしまう
2. 1 回に 1 問だけ聞く。質問の頭に「N 問目です」と番号を付ける
3. 答えは選択肢から選べる形にする。選択肢は 2〜4 個で、それぞれに短い説明を付け、最後に必ず「それ以外」(自由に書ける) を置く。選択肢を出す仕組みがあれば (Claude Code の AskUserQuestion など) それを使い、無ければ本文に「A」「B」「C」「それ以外」で書く
4. 価値を先に、機能を後に聞く。観点の順は「問い詰める観点」に従う。ただし本人の答えが先の観点に触れたら、その答えを受けて順番を入れ替えてよい
5. 本人が選択肢から外れた答えや、長い自由記述を返したら、それが一番の材料である。書き換えずに受け取り、次の質問をその答えの上に作る。答えに URL や資料があれば読み、次の選択肢の材料にする (要約は見せない)
6. 答えから読み取ったことを概要に書く前に、読み取りに推測が混ざっていれば、次の質問で確かめる。特に、価値の重み、件数や規模、地図の役割 (主役か脇役か) は推測しやすく、外しやすい
7. 本人が「重要なのはこれ」と価値を並べ直したら、それまでの Must を聞き直す
8. 公開文書で分かる事実 (料金、規約、仕様) は本人に聞かず、後の段階のスキルで確かめる。本人に聞くのは、本人にしか分からないこと (誰に届けたいか、何が嬉しいか、期限、予算、利用形態、端末) に絞る
9. 終了条件がそろったら、ひな形に沿ってプロダクト概要を書き、要点を短く示して「このまま次の段階に進んでよいか」を選択肢 (このままでよい / 直したいところがある) で確かめる。直しが来たら、直した箇所を示してもう一度確かめる。確かめがとれたら、技術選定の前に geo-software-research-competitor で似たサービスを探し、続けて geo-software-eval で完成の条件を評価のシナリオにする (本人と一緒に)

## 問い詰める観点

上から順に聞く。各観点の質問と選択肢の例は [question-bank](references/question-bank.md) にある。

1. 誰に届けるか: 自分自身、身近な誰か、不特定多数。作るものの目的 (実際の利用者向けか、デモや作例か)
2. どの場面の、どんな困りごとか: 場面 (出かけるとき、振り返るとき、データを扱うとき) から絞り、困りごとを 1 つに決める
3. 価値の芯: その困りごとが解けた状態で、何が一番嬉しいか。候補が複数出たら、本人に重要な順に並べてもらう
4. 中心になる操作: 価値を生む操作は何か (例: 自分で押す、位置で自動、写真を撮る)。操作の決め方で、後の段階のルールの強制 (信頼の境界) が決まる
5. 地図の役割: 主役か、一覧と半々か、脇役か。現在地が要るか
6. 表示するデータ: 何を、どれくらいの件数、どこから。本人の過去の記録があれば、それで件数を数える。分類が要るなら、その対象の性格から立てる
7. 記録と共有: 書き込みがあるか、誰が書くか、どこに残すか (端末だけ、自分だけで同期、公開)。写真などの置き場所
8. 最初の版の範囲と期限: どの地域、どの件数、いつまでに
9. 端末と利用形態: 端末 (Android、iPhone、PC)、個人か商用か、配布形態 (SaaS、OSS、ストア)、予算、SLA
10. 機能の優先度: 候補の機能を並べ、期限までに要る Must を複数選択で選んでもらう。残りを Should と Could に分ける

## 出力

[assets/product-brief-template.md](assets/product-brief-template.md) のひな形に沿ったプロダクト概要。置き場所は AGENTS.md の「スキル間の受け渡し」に従う (利用者の作業ディレクトリの `product-brief.md`)。本人の答えに含まれる私的な事柄 (旅行の日程、宿の場所、住所) は、作業に要る範囲で書き、公開するリポジトリには写さない。

## やってはいけないこと

- 価値が固まらないうちに技術選定に進む
- 一度に複数の質問を並べる。選択肢の無い質問だけを投げる
- 読んだ材料の要約やエージェントの見立てを、質問の前に本人に見せる
- ユーザーの答えを推測で埋める
- 価値の重みを推測で決める。2026-11-10 の聞き取り (旅の実績解除アプリ) では、「解除の瞬間の演出」と「地図が主役」を価値の芯と読んで、2 回外した。本人にとっての最重要は「大量の実績の一覧で、自分から取りに行く行動を支える」ことで、演出は副次的だった。価値は、重要な順に本人に並べてもらう
- 価値の順番が変わったのに、機能の Must を据え置く。価値を並べ直したら、Must を聞き直す (同じ聞き取りで、Must は 5 つから 2 つに減った)
- 件数や規模を推測で書く。本人が示した例 (過去の記録など) で数えてから書く (「数百件」と書いて、例では最多 80 件だった)
- 分類を、別の例から引き写す。分類はその対象の性格から立てる (広島の「交通」は路面電車があったからで、大阪には「食い倒れ」や「水都」が立つ)
- 本人の言葉を、別の対象に読み替える (「カテゴリごとに星」と頼まれたと読んで、実際は「実績ごとに星を付けてカテゴリ内で並べる」だった例がある)。対象が 2 通りに読めるときは聞く
- 公開文書で分かる事実を本人に聞く。料金や規約は後の段階で確かめる
- 本人の思いつきや、価値の変化のメモを、実装の依頼として受け取る。「実装の依頼ではない」と添えられたもの、依頼の形でないものは作り始めず、プロダクト概要の価値の欄に日付つきで書き残す。進めると言われたら、価値の順位を聞き直してから Must を見直す (旅の実績解除アプリで、本人が「計画を立てる段階が一番楽しい」と書いたが、実装の依頼ではなかった)
