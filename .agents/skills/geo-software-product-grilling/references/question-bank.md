# 質問の候補

SKILL.md の「問い詰める観点」ごとに、質問の例と選択肢の作り方を並べる。どの質問も 1 回に 1 問で、選択肢 2〜4 個と「それ以外」を付ける。選択肢は、依頼と本人の材料から作る。下の例はそのまま使わず、依頼に合わせて書き換える。

## 選択肢の作り方

- 選択肢どうしは、互いに重ならない別の答えにする (同じことの言い換えを並べない)
- 各選択肢に 1 文の説明を付け、選んだら何が決まるかが分かるようにする
- 本人の材料 (過去の記録、参考の URL) から読み取った見立ては、選択肢の 1 つとして混ぜるだけにし、「おすすめ」と書かない。見立てが外れていても、本人が「それ以外」で正せる
- 複数選んでよい質問 (Must の選択など) は、複数選択だと明記する
- 本人が選択肢を選ばずに長く書いたら、その文が次の質問の材料になる。選択肢に引き戻さない

## 1. 誰に届けるか

- 「まず誰に届けたいですか?」: A 実際の利用者 (特定の困りごとを持つ人が本当に使う) / B 作例やデモの読み手 / C 開発者向けの手本
- 「その利用者はどんな人ですか?」: A 自分自身 / B 身近な誰か (同僚、家族、地域の人) / C 不特定多数 (旅行者、住民、通勤者)

## 2. 場面と困りごと

- 「どの場面の困りごとを解きたいですか?」: A 出かけるとき / B 振り返るとき / C データを扱うとき。場面の候補は、本人の材料に出てくる活動から作る
- 「その場面の困りごとは、どれが一番近いですか?」: A 行き先を決められない / B その場で探すのが大変 / C 移動そのものが大変

## 3. 価値の芯と順位

- 候補の価値が 2 つ以上出たら、本人に重要な順に並べてもらう。「最重要はどれですか?」を先に聞き、残りを「重要」と「副次的」に分ける
- 本人が価値を並べ直したら、それを最優先で概要に書き、機能の Must を聞き直す (観点 10)

## 4. 中心になる操作

- 「〇〇は、どうやって起きるのがいいですか?」: A 位置で自動 / B 写真を撮って / C 自分で押す。位置で自動にする場合は不正の防止 (信頼の境界) が要るかを、後の段階に渡す
- 「提案は、何をもとに作るのがいいですか?」: A AI が提案 / B オープンデータから / C 両方

## 5. 地図の役割

- 「主に見るのはどちらですか?」: A 地図が主 / B 一覧が主 / C 半々 (切り替え)。答えに「現在地」が出てきたら、閲覧するだけの人にも位置を求めるかを確かめる

## 6. 表示するデータ

- 件数は聞かずに数える。本人の過去の記録があれば、それで数えて概要に書く。記録が無ければ「数十件 / 数百件 / 数千件」の選択肢で聞く
- 分類 (ジャンル) が要るときは、その対象の性格から候補を作り、「当てはまるものを選んでください (複数可)」で聞く。本人の関心 (例: 近代史) が答えに出たら、それを分類に立てる

## 7. 記録と共有

- 「記録はどこに置きますか?」: A 端末の中だけ / B 自分だけで同期 / C 公開して見せる
- 「公開するページに、写真も載せますか?」: A 載せる / B 実績だけ / C そのつど選ぶ。写真の位置情報 (EXIF) の扱いもここで聞く
- 公開や共有の時期: 「最初の版に間に合う必要がありますか?」: A 後でよい / B 最初の版で

## 8. 最初の版の範囲と期限

- 「最初に動く版では、どの範囲が入っていればいいですか?」: A 次に使う予定の場所だけ / B 過去の記録を移す / C 最初から全部
- 「いつまでに使えればいいですか?」: A 1 週間以内 / B 1 か月以内 / C もっと先。期限で Must の量を決める

## 9. 端末と利用形態

- 「使う端末はどれですか?」: A Android / B iPhone / C 両方
- 利用形態 (個人か商用か)、配布形態 (SaaS、OSS、ストア)、予算、SLA は、まとめて自由記述で答えてもらってもよい
- 「SaaS」のように 2 通りに読める言葉が出たら聞く: A 自分用の公開サービス / B いずれ他の人も登録できる / C 最初から複数人

## 10. 機能の優先度

- 価値から導いた候補の機能を 4 つまで並べ、「最初の版に間に合わないと困るもの (Must) はどれですか? (複数選択可)」と聞く。価値の順位で最重要に当たる機能は、本人が選ばなくても Must の候補として確かめる
- 価値を並べ直した後は、同じ質問をもう一度する。前の答えを据え置かない

## 実例: 2026-11-10 の聞き取り (旅の実績解除アプリ)

本人は「MapLibre で何か作りたい」とだけ言って始め、20 問ほどで概要がまとまった。流れは次のとおり。

1. 誰に届けたいか → 実際の利用者
2. どんな人か → 自分自身
3. どの場面か → 出かけるとき
4. どんな困りごとか → 選択肢を選ばず「旅先の定番の名所を訪れることを、ゲームの『実績解除！』のように演出するアプリがほしい。どこを訪れるべきかも提案してほしい」と、過去の旅の記録 (Scrapbox の実績の一覧) の URL を添えて答えた。記録を読み、以後の選択肢の材料にした
5. 実績はどう解除されるか → 自分で押す (記録に「泣く」「飲む」のような位置で決まらない実績があった)
6. 提案は何をもとに作るか → 選択肢を選ばず「定番は決定論的なので、AI がオープンデータから全国の実績を前もって作ればよい」
7. 画像は → 名所の写真と自分の写真の組み合わせ
8. 気持ちいい瞬間は → 解除の瞬間と、後から見返して埋まっていることの両方
9. 記録の置き場所は → 公開して見せる
10〜13. 最初の範囲、行き先、時期、端末 → 次の旅行先 (大阪市) だけ、数日後、Android
14〜16. 公開の時期、写真の公開、Must の選択
17. ここで本人が価値を並べ直した: 最重要は「積極的な実績解除の行動を提案し支えること」で、演出や見返すことは副次的。エージェントは 2 回、価値の芯を読み違えていた
18. 「提案し支える」の中身 → 「大量の解除すべき実績が一覧になっていればよく、人はそれを眺めて好きに選ぶ」
19. Must を聞き直した → 「簡潔で見やすい一覧」と「解除が適切に記録されること」の 2 つに減った
20. 地図の役割 → 半々、一覧と地図を切り替え、地図には現在地
21. 件数: エージェントが「数百件」と書き、本人が「記録では 100 件を超えるものは無い」と正した。数え直すと最多 80 件ほどだった
22. SaaS の意味 → いずれ他の人も登録できるサービス (最初の版は自分だけ)

このあと、置き場所、地図データ、ライブラリの段階に進み、作って公開した (examples/unlock-your-trip)。
