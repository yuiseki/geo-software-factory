# geo-software-security-audit

ダークファクトリーでは、人間がコードをレビューしない。だから、セキュリティも人間の目ではなく、実装と切り離した監査で確かめる。監査は、何が守られていれば良いかを人間が昼に決め、夜に実装者と別の監査者が、誰でも使える入口から攻め手の目で調べる。

サービスは、個人情報が漏れなくても、データが改ざんされなくても壊れる。登録し放題から決済を試され放題になる、数千文字の要求一つで裏の検索や DB が止まる、パスワードの再設定のメールが何万通も送られて送信元がスパム扱いになる。地図のプロダクトでは、これに、全世界を囲む範囲の要求、頂点が百万ある図形、地図の読み込みごとに課金されるタイルの鍵の流用、利用者の正確な位置の推定が加わる。教科書にもバグバウンティにも出にくいこれらを、漏れや改ざんと同じ重さで調べる。

## 監査の原則

1. 自分たちのサービスだけを調べる。他人のサービス、上流の供給元 (タイルの配信、ジオコーダ、公開の OSM のサーバー) に試しの要求を送らない。上流への影響は、自分のサービスが上流を何回呼ぶかで見積もる。
2. 監査者は実装者と別にする。実装の会話の履歴を渡さず、別の文脈 (できれば別のモデル) で動かす。実装者は「こう作ったから大丈夫」と読んでしまう (geo-software-eval の評価者の独立と同じ)。
3. コードは候補を見つけるために読み、問題があるかは振る舞いで確かめる。入口から DB、保存先、外部の呼び出し、画面への出力 (sink) までをコードで追って候補を挙げ、手元かプレビューで再現して確かめる。再現できない推測は問題として出さず、追加調査の候補にする。
4. 壊れ方を広く数える。漏れ、改ざん、乗っ取りに加えて、止まる、遅くなる、請求が膨らむ、送信元の評判が落ちる、第三者 (カードの持ち主、メールの受け手、上流の供給元) が困る、も問題に数える。
5. 判定を 4 つに分ける。「問題あり」「防御されている」「該当なし」「未確認」。調べていないところを「問題なし」と書かない。
6. 確かめた問題は、評価のシナリオにして残す。直したあとに戻らないことを、実装から切り離した評価で毎回確かめる。
7. 対策そのものを疑う。全体で 1 つの上限や枠は、攻撃者が使い切ると全員が止まる。対策が新しい壊し方にならないかを確かめてから勧める。

## 進め方

### 昼: 守るものを決める

人間に聞くことを 1 度の機会にまとめる (AGENTS.md の昼の擦り合わせ)。選択肢で答えられる形にする。

- 誰が登録できるか (誰でも、招待だけ、組織の中だけ)。登録の直後に使える機能はどこまでか。
- 濫用の予算: 1 日に使ってよいメールの通数、外部の API (タイル、ジオコーダ、ルート検索、LLM) の費用、決済の試行の扱い。上限に届いたときに止めるか、遅くするか、通知するか。
- 利用者の位置の扱い: 保存するか、どの精度で見せるか、他の利用者との距離を出すか、写真の位置情報 (EXIF) を残すか。
- 公開を止める深刻度: どの深刻度の問題が残っていたら、夜のうちに本番に出さないか (マージと公開の関門)。
- 再現してよい場所: 手元とプレビューだけか、本番で読み出しだけの確認をしてよいか。本番での負荷や大量の要求の試しは、既定で行わない。

### 夜: 監査する

geo-software-build で作り終えたあと、geo-software-deploy の前に行う。

1. 入口を洗い出す ([entrypoints](references/entrypoints.md))。認証なしで呼べるものと、誰でもすぐ作れる一般の利用者で呼べるものを、画面ではなくルートの定義と設定から列挙する。それぞれ、画面を通さずに直接呼べるかを確かめる。
2. 5 つの領域を当てる ([auth](references/auth.md)、[injection](references/injection.md)、[abuse](references/abuse.md)、[exposure](references/exposure.md))。各領域の問いを入口ごとに当て、コードを入口から sink まで追って候補を挙げる。
3. 候補を手元かプレビューで再現する。監査用に分けた利用者とデータで行い、要求の数は再現に要るだけに絞る (大量の要求は、少ない回数での応答時間と資源の使い方から見積もる)。
4. 判定する ([triage](references/triage.md))。4 つの状態に分け、深刻度を付け、深刻度と対策を見直す。
5. 確かめた問題を、実装者に返す。返すのは、どの入口に、どんな要求を送ると、何が観測されたか (症状) と、守るべき振る舞いである。
6. 実装者が直したら、同じ再現の手順で確かめ直し、問題を評価のシナリオにして geo-software-eval のシナリオの置き場所に足す (例: 「1 万文字の検索語は、100 ms 以内に 400 を返し、裏の検索を呼ばない」)。足すことは夜でもよい (緩めることはしない)。
7. 公開を止める深刻度の問題が残っていたら、本番には出さず、プレビューまでに留めて朝の報告に書く。
8. 結果を [assets/audit-report-template.md](assets/audit-report-template.md) の形で残し、朝の報告に入れる。

### 公開のあと

- デプロイの直後に、本番に対して読み出しだけの露出の確認をする ([exposure](references/exposure.md): ヘッダ、`.git` や `.env` や source map が取れないか、プレビューの URL の公開)。負荷の試しはしない。
- geo-software-swarm で群れを動かすなら、監査の役割を置く。依存の脆弱性の通知、新しく足された入口、評価のシナリオに無い入口を定期的に当てる。
- 公開のリポジトリでは、確かめた脆弱性を公開の issue に書かない。再現の手順は、非公開の報告の仕組み (GitHub の private vulnerability reporting、security advisory など) か、人間だけが読める場所に置く。群れの掲示板が公開なら、そこには「非公開の報告がある」とだけ書く。

## 監査そのものを確かめる

- わざと脆弱性を入れた版 (認可の確認を 1 つ外す、ポップアップに属性を HTML のまま入れる、範囲の上限を外す) を作り、監査が見つけるかを確かめる。見つけられないなら、監査の問いか入口の洗い出しが足りない (geo-software-eval の eval-of-eval と同じ考え方)。
- 「防御されている」と書いたものは、防御を確かめた観測 (返った状態コード、応答時間、拒まれた記録) を添える。根拠の無い「防御されている」は「未確認」に戻す。

## 出力

- 監査の報告: 入口の一覧、領域ごとの 4 つの状態、確かめた問題 (再現の手順、深刻度と理由、勧める対策と、その対策が新しい壊し方にならないかの確認)、未確認と追加調査の候補。
- 評価のシナリオへの追加: 確かめた問題ごとに、守るべき振る舞い。
- プロダクト概要の更新: 「夜に決めたこと」(深刻度の判断、公開を止めたか)、「止まったこと」(本番に出さなかった理由、人間に決めてほしいこと)。

## 注意

- 監査が問題を見つけなかったことは、安全の証明ではない。調べた入口と領域、調べていない範囲を書く。
- 法令と規約 (個人情報、位置情報、測量法、地図 API の規約) は geo-software-legal-check で扱う。ここでは技術の振る舞いを調べる。
- 認証の仕組みの選び方は geo-software-auth、鍵の制限と利用量の見張りは geo-software-ops で扱う。監査で見つけた不足は、それらに戻して直す。
- 秘密の値は、見つけても報告に書かない。どこに、どの名前の秘密があったかだけを書く。
