# 濫用と使い切り

データが漏れなくても、サービスは壊れる。ここでは、正しい利用者の操作を、正しくない回数、大きさ、順番で行われたときに、何が止まり、誰が払うかを調べる。

## 登録と決済

- 登録し放題: 1 人で何個でもアカウントを作れると、利用者ごとの上限が意味を失う。さらに決済があると、作ったアカウントでカードの番号を次々に試される (クレジットマスター攻撃)。困るのは、カードの持ち主、決済の事業者、そして不正の温床と見なされる自分のサービスである。
- 確かめること: 決済の前に、メールか電話番号の確認を要するか。登録した直後の決済を制限しているか。決済して、すぐ解約して、また決済する、という動きを見つけて止められるか。

## 巨大な要求

数万文字や数千回は要らない。数百文字、数千文字の要求 1 つで、裏の検索や DB や外部の API が止まることがある。手前のサーバーが横に増えても、その裏にある DB、KV、検索、外部の API は増えない。

- 文字の長さ: クエリの引数、検索語、名前、説明に、サーバー側で長さの上限があるか。多くの引数は 1,000 文字未満で足りる。画面の検査だけでなく、サーバーで検査しているか。
- 地図に特有の大きさ:
  - 範囲 (`bbox`) が全世界、あるいは逆転した範囲や範囲外の値のときに、何件を読み、何件を返すか。件数 (`limit`) に上限があるか。
  - 投稿や取り込みの図形の頂点の数、GeoJSON やファイルの大きさ、ZIP を展開したあとの大きさ。
  - ルート検索の経由地の数、到達圏の時間や距離、行列計算の地点の数。
  - その場でタイルを作る仕組みでは、低いズーム (全部の地物が 1 枚に入る) の要求の重さ。
  - 写真や画像の縦横の大きさ (展開するとメモリを使い切る画像)。
- 確かめ方: 本番ではなく手元かプレビューで、大きな要求を 1 回ずつ送り、応答の時間、CPU の時間、裏への呼び出しの数を測る。それを、許される回数で掛けて見積もる。

## メールと SMS

- パスワードの再設定、招待、確認のコードの再送、共有の通知、お知らせを、何回でも呼べないか。短い間に何万通も送れると、送信元がスパム扱いになり、正しい利用者に大事なメールが届かなくなる。送信の多くは従量で課金される。
- 確かめること: 送信の機能ごとに回数の上限があるか (例: 1 分に 10 人も招待できれば足りる)。利用者の操作ごとに通知を送らず、1 日や 1 週間でまとめて送れないか。

## 従量で課金される上流

地図のプロダクトは、自分の鍵で上流を呼ぶことが多い。呼ぶ回数を決めるのが利用者 (や攻撃者) なら、請求を決めるのも彼らである。

- タイルや地図の読み込み: 地図の読み込みやタイルの要求ごとに課金される供給元の鍵が、配布物に入っている。リファラーの制限はブラウザの外からは偽れるので、鍵が他の場所で使われたときの上限と通知を確かめる (geo-software-ops の api-key-management と usage-monitoring)。
- ジオコーダ、ルート検索、標高、LLM、画像の処理: 誰が、認証なしで、何回呼べるか。上流の枠を使い切られたとき、自分のサービスの全員が止まらないか。
- 配信の転送量と読み出しの回数: PMTiles のような Range 要求の配信や、大きなファイルの配布は、読み出しの回数や転送量で課金される置き場がある。料金の単位を供給元の文書で確かめ、確かめた日を書く。
- 共有の資源の一覧: メールの枠、SMS、LLM と外部の API、決済、重い画像と動画と GIS の処理、DB、保存先、キュー。それぞれ、誰が呼べて、どの上限があるかを表にする。

## 応答の違いからの推測

- 状態コード、エラーの文言、応答の大きさ、転送の先、応答の時間の違いから、利用者が存在するか、招待のコードや共有の ID が正しいか、API の鍵が有効かを、大量に判定できないか。
- 位置の推測: 「近くの利用者」「あなたからの距離」を返す機能は、場所を変えて何度か問い合わせると、相手の正確な位置を三点測量で割り出せる。距離を丸めるだけでは足りず、問い合わせの位置を偽れないか、回数に上限があるかも見る (位置の露出は [exposure](exposure.md) でも見る)。

## 上限の置き場所と、対策の見直し

- 回数の上限 (rate limit) を、どこで保証しているか: アプリ、CDN や WAF、認証の提供元、上流の供給元。提供元の仕組みの仕様は、版と文書で確かめる。画面だけ、あるいは 1 つの端末の記憶だけに置いた上限は、上限ではない。
- 対策が新しい DoS にならないか: サービス全体で 1 つの上限や枠は、攻撃者が使い切ると、正しい利用者が全員止まる。上限は利用者ごと、IP ごと、機能ごとに分け、認証した利用者と認証していない要求の枠を分け、全体の枠に届いたときに何を優先するかを決める。
- 濫用の予算 (昼に決めた、1 日のメールの通数や外部の API の費用) に届いたときの振る舞い (止める、遅くする、人間に通知する) が、実装されているか。
