# 認証と認可

## 認証

- 登録、ログイン、メールの確認、パスワードの再設定を、画面を通さずに API で直接呼べないか。画面の CAPTCHA や入力の検査を飛ばせないか。
- メールの確認の前に使える機能が無いか (地物の投稿、共有のリンクの作成、招待の送信)。登録した直後の利用者に、どこまで許すかは昼に決めた方針と照らす。
- トークン (セッション、JWT、OAuth、OIDC) の検証: 署名を公開の検証鍵 (JWKS) で確かめているか、発行者 (issuer)、宛先 (audience、または認証の提供元が使う許可したオリジンの項目)、有効期限を確かめているか。開発用の環境で発行したトークンを本番が受け取らないか。OAuth の戻り先 (redirect_uri) を完全一致で確かめているか。
- 取り消しのあと: 利用者の削除、無効化、パスワードの変更、権限の変更、ログアウトのあとに、発行済みのセッション、JWT、API の鍵、共有のリンクが使い続けられないか。
- パスワードの再設定、招待、共有のトークン: 推測できないほどランダムか、期限があるか、1 回限りか、保存するときはハッシュにしているか。

## 認可

- 他人のデータ (IDOR、BOLA): ログインした利用者が、URL、クエリ、本文の ID (旅の ID、レイヤーの ID、地物の ID、写真の ID、組織の ID) を書き換えるだけで、他人のものを読めないか、変えられないか、消せないか。入口から DB と保存先の操作までをコードで追い、条件に持ち主の確認が入っているかを見る。
- 権限の出どころ: 管理者や役割の判定が、利用者自身が書き換えられる値 (プロフィールの属性、メールアドレスの文字列、本文、cookie、localStorage、検証していないトークンの項目) に頼っていないか。認証の提供元には、利用者が書ける属性と、サーバーだけが書ける属性を分けているものがある (例: Clerk の unsafeMetadata は利用者側から書ける)。どちらを判定に使っているかを、提供元の文書と照らして確かめる。
- 画面で隠すだけの制御: 管理の画面や、持ち主だけの操作が、ボタンを隠すだけでサーバーの認可が無い、ということが無いか。非公開のデータは、画面で隠すだけでなくサーバーの読み出しで除いているか (geo-software-build の原則)。
- 認証なしで呼べる入口 ([entrypoints](entrypoints.md)) から、非公開のデータの取得や管理の操作ができないか。

## 地図に特有の漏れ方

- タイルからの漏れ: 一覧の API では非公開の地物を除いていても、ベクタータイルや PMTiles に全部の地物と属性を焼いていると、タイルを直接読めば見える。タイルに入れる属性は、画面に出すものだけにする。非公開の地物は、利用者ごとに出し分けるか、タイルに入れない (geo-software-auth の tile-access-control)。
- 範囲の検索からの漏れ: 一覧には出ない地物が、`bbox` の検索や近くの検索の結果に混ざらないか。
- 共有のリンク: 共有した地図の ID から、共有していない他の地図や、持ち主の他の旅が辿れないか。
