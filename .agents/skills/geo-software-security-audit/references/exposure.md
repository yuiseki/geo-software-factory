# 露出

意図せず外から見えるもの、取れるものを調べる。本番に対しては読み出しだけで確かめる。

## 公開の面

- リポジトリとデプロイの設定から、外に出るサービス、ポート、名前を書き出す ([entrypoints](entrypoints.md))。
- 取れてはいけないものが取れないか: `.git`、`.env`、source map、デバッグや metrics のエンドポイント、管理の画面、DB や KV や保存先に直接つながるエンドポイント、ステージングの環境。
- プレビューや版ごとの URL: 本番に割り当てていない版の URL が、誰でも開ける状態になっていないか。独自ドメインを割り当てたあと、元の URL (Workers なら workers.dev) が開いたままか閉じたかを確かめ、どちらにするかを決めて書く (geo-software-deploy の cloudflare-workers)。

## ヘッダと通信

- HTTPS と HSTS、cookie の属性 (`Secure`、`HttpOnly`、`SameSite`)。
- CSP: 地図のライブラリは、Web Worker や blob の URL、タイルとフォントと画像の取得先を要することが多い。ライブラリの文書の CSP の例を出発点にし、`unsafe-eval` のような緩みを要る理由ごとに確かめる (geo-software-library の各 reference の「環境の違いと保守」)。
- CORS: 公開のタイルは誰からでも読めてよいが、認証の要る API に、資格情報つきで任意のオリジンを許していないか。

## 配布物とログの中の秘密

- 画面の配布物 (JavaScript の束、source map)、API の応答、エラー、ログ、CI の出力に、秘密の鍵、トークン、パスワードのハッシュ、個人情報、内部用の属性が出ていないか。ビルドした配布物そのものを検索して確かめる。
- 配布物に入れてよい鍵 (タイルの供給元の公開用の鍵、認証の提供元の Publishable Key) と、入れてはいけない鍵を分ける。入れてよい鍵も、使える範囲 (リファラー、API の種類、上限) を制限する (geo-software-ops の api-key-management)。
- 見つけた秘密は、値を報告に書かない。どこに、どの名前の秘密があったかを書き、鍵の取り替えを人間に頼む。履歴に入った秘密は、消しても取り替えが要る (geo-software-deploy の publish-repo)。

## 利用者の位置の露出

地図のプロダクトでは、位置が最も漏れやすい個人の情報である。

- 現在地や移動の記録を、昼に決めた精度より細かく保存していないか、返していないか。
- 投稿された写真の位置情報 (EXIF) を、そのまま配っていないか。残すか消すかは昼に決めた方針に従う。
- 時刻と位置の組から、自宅や職場が推測できないか (毎晩同じ場所で終わる記録など)。
- 距離を返す機能による三点測量 ([abuse](abuse.md))。
- ログや分析の送信に、位置が入っていないか。

## 依存と CI

- 依存のライブラリ、ランタイム、CI、ビルド、デプロイの仕組みを、セキュリティの観点で見る。既知の脆弱性や保守の終わった版は、版が一致するだけで問題ありとせず、脆弱なコードの経路に外からの入力が届くかまで確かめる。
- CI の外部のアクションは、版を固定しているか。CI に渡す秘密の範囲は、要る仕事に絞っているか。
