# 注入

外からの入力が、どこに流れ込むか (sink) を追う。地図のプロダクトでは、利用者の入力に加えて、外から取り込んだ地図データ (OSM のタグ、オープンデータの属性、写真の OCR や EXIF) も外からの入力である。

## 地図に特有の流れ込み先

- 地物の属性から画面へ: ポップアップやツールチップに、属性を HTML として入れていないか。MapLibre の `Popup` には `setHTML` と `setText` があり、Leaflet の `bindPopup` は文字列を HTML として扱う。名前や説明の属性は、文字として入れるか、DOM の要素を作って入れる。外のデータの属性に、スクリプトを含む文字列が入っていることがある。
- スタイルとタイルの URL: 利用者がスタイルの JSON、タイルの URL のひな形、画像の URL を指定できると、任意の場所から読み込ませられる。要求に認証のヘッダを足す仕組み (MapLibre の `transformRequest` など) が、URL の行き先を確かめずにヘッダを付けると、鍵が他の場所に送られる。
- サーバー側の中継 (タイル、画像、ジオコーダ): 利用者が URL や行き先を指定できると、内部のネットワーク、`localhost`、クラウドの metadata の取得口 (SSRF) に届く。行き先は許可した一覧で決め、転送 (redirect) の先も確かめる。
- 空間の SQL: 範囲、座標、WKT、GeoJSON を、文字列の連結で SQL に入れていないか。値はパラメーターで渡す。パラメーターで渡しても、頂点の多い図形は重い (これは [abuse](abuse.md) で見る)。
- 検索語: 全文検索 (SQLite の FTS5 の `MATCH` など) は、検索語そのものを問い合わせの構文として読む。利用者の入力をそのまま渡すと、構文の誤りで 500 になったり、重い問い合わせになったりする。語として引用して渡す。
- 取り込むファイル: KML と GPX は XML なので、サーバーで読むときに外部の実体 (XXE) を読まない設定にする。Shapefile の ZIP は、中のファイル名で保存先の外に書き出せないか (zip slip)。ファイル名と保存先のパスを、利用者の入力から作っていないか (path traversal)。
- 書き出すファイル: CSV に書き出す名前や説明が `=`、`+`、`-`、`@` で始まると、表計算のソフトで式として動く。書き出しで無害にする。

## 一般の流れ込み先

- HTML、SQL、NoSQL、テンプレート、Markdown、メールの本文と件名、HTTP のヘッダ、ログ。それぞれで、パラメーター化、エスケープ、無害化が足りているかを、入力から sink まで追って確かめる。
- リポジトリ全体から、`eval`、`new Function`、`innerHTML`、`dangerouslySetInnerHTML`、`document.write`、`exec`、`spawn`、安全でない逆シリアル化を探し、外からの入力が届くかを確かめる。
- ログインのあとの戻り先 (`redirect_url` などの引数) が、外の場所に飛ばせないか (open redirect)。
- 取り込んだ内容を LLM に渡す機能がある場合: 地物の属性、写真の OCR、Web のページに書かれた指示に従わないか。それらはデータとして扱う (AGENTS.md の統治の層と同じ考え方を、プロダクトの機能にも当てる)。
