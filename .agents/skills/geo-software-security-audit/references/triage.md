# 判定と深刻度

## 4 つの状態

領域ごと、入口ごとに、次のどれかを付ける。

| 状態 | 付けてよいとき |
|---|---|
| 問題あり | 手元かプレビューで再現し、観測がある |
| 防御されている | 攻めを試し、拒まれたこと、または上限が効いたことの観測がある |
| 該当なし | その入口や機能が存在しない (例: 決済が無い) |
| 未確認 | 調べていない、再現できなかった、本番でしか確かめられない |

観測の無い「防御されている」は「未確認」にする。コードを読んで「大丈夫そう」は、未確認である。

## 深刻度の付け方

次の 3 つで付ける。

- 誰が悪用できるか: 認証なしの誰でも、誰でもすぐ作れる一般の利用者、特定の役割の利用者、内部の人。
- 誰が困るか: 他の利用者 (データ、位置、アカウント)、運営 (請求、停止、送信元の評判)、第三者 (カードの持ち主、メールの受け手、上流の供給元)。
- どこまで広がるか: 1 人の利用者、一部の利用者、全員、サービスの外。

High や Critical と付けたものは、なぜ 1 段低くないのかを書く。低く付けたものも、悪用の前提 (要る権限、要る回数) を書く。

## 見直し

- 仕様と誤検知を除く: 公開の地図のタイルが誰でも読める、公開の地物の一覧が取れる、のように意図したものを問題にしない。意図かどうかは、昼に決めた方針とプロダクト概要で確かめる。
- 再現を確かめ直す: コード上の根拠、再現の条件、影響の範囲を書き、再現できない推測は追加調査の候補にする。
- 重複を確かめる: 既存の issue、PR、非公開の報告と重ならないか。
- 対策を確かめる: 勧める対策が、新しい壊し方にならないか ([abuse](abuse.md) の対策の見直し)。正しい利用者を巻き込む上限、使い切れる全体の枠、上流への呼び出しを増やす確認、を避ける。

## 評価のシナリオへの変換

確かめた問題は、直したあと戻らないように、geo-software-eval のシナリオにする。観測できる振る舞いで書く。

- 「他人の旅の ID で `GET` すると 404 を返し、本文に旅の名前を含まない」
- 「全世界の範囲の検索は、返す件数が上限以下で、応答が 1 秒以内」
- 「名前に `<img src=x onerror=...>` を持つ地物のポップアップで、スクリプトが動かない (コンソールに実行の記録が無い)」
- 「同じ宛先への再設定のメールは、1 時間に N 通を超えて送られない (送信の代役の記録で数える)」

メールや決済のように外に影響するものは、代役 (geo-software-eval の twins) で数える。

## 公開を止めるか

- 昼に決めた「公開を止める深刻度」以上の問題が残っていたら、本番に出さない。プレビューまでに留め、朝の報告に書く。
- 止めるかどうかを夜に迷ったら、止める側に倒す。理由を「夜に決めたこと」に書く。
