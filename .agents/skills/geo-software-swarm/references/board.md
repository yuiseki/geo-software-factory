# 掲示板

群れは、中央の指揮者ではなく、共有の掲示板に残した痕跡で協調する (社会性昆虫のスティグマジーと同じ考え方)。issue が仕事と証拠を、PR が変更を、チェックとレビューが判定を運ぶ。この 3 種類を持てる場所なら何でもよく、GitHub の issue、PR、チェック、レビューがそのまま使える。

## 各回の動き

各役割は、予定の時刻に起きて、掲示板を読み、1 つだけ仕事をして、終わる。記憶は持たない。

1. 停止スイッチを確かめる ([governance](governance.md))。止まっていれば何もせずに終わる。
2. 自分の役割に関係する issue と PR を読む (ラベルで絞る)。
3. 1 つだけ選んで行う (issue を 1 つ立てる、PR を 1 つ出す、1 つの PR を判定する)。
4. 次の回のために、したこと、根拠、残ったことをコメントに書く。
5. 終わる。

## 書き方

- issue: 症状 (画面、操作、期待、観測)、再現の条件、証拠 (スクリーンショット、ログ)、目的 (どの目的に属するか)、重さ。重さは群れが勝手に決めず、昼に人間が決めた基準 (例: 地図が出ない > 帰属表示の欠け > 文言の誤り) で付ける。
- PR: どの issue を閉じるか、何をどう直したか、足したテスト。1 つの PR で直す issue は、同じ根本の原因のものに限る。
- ラベル: 役割、目的、重さ、状態 (調べ中、直し中、評価待ち、届いた)。
- メモ: 回をまたぐ文脈はコメントに書く。日付を付ける。古いメモは状況が変わっていることがあるので、最新の状態と照らしてから従う。

## 重複と競合

- 同じ症状の issue を立てる前に、掲示板を検索する。
- 同じ issue に複数の役割が手を出さないよう、取りかかるときに割り当てかラベルで印を付ける。
- 群れは自分で仕事を増やす (論文の事例では新しい issue の 95% をエージェントが立てた)。issue の数の増減は、進み具合の目安にならない (geo-software-eval の progress)。
