# 既存・レガシー地図ソフトウェアを正本とする特性テストと移植 TDD

既存の地図ソフトウェアの改修・機能追加、依存関係のマイグレーション、モダンアーキテクチャへの全面作り直しのいずれでも、**「既存のソフトウェアの実際の振る舞いを正本 (Oracle) とする」** ことから始める。仕様書や記憶ではなく、動いている旧ソフトの入出力をテストで固定してから手を動かす。

## 4 段階の進め方

### 1. 旧ソフトウェアのテスト確認と特性テスト (Characterization Test) の追加

1. まず既存リポジトリのテストの有無と、テストが現在の環境で通るかを確かめる。
2. **テストが無い、または改修・移行対象の領域を覆っていない場合**: 本体のコードを 1 行も変える前に、旧ソフトウェアをそのまま動かした状態で「現在の振る舞いを記録し合格とする特性テスト (Golden Master)」を追加する。
   - **空間演算・座標変換**: 代表的な入力座標 (平面直角座標、旧測地系、境界値、欠損値) を通し、出力の緯度経度・距離・面積・件数をスナップショットとして固定する。
   - **API / 検索 / フィルタ**: 代表的なクエリ (`q`、bbox、種別、ページング、異常入力) に対する HTTP 状態コード、GeoJSON の `features` 件数・プロパティ・座標を記録する。
   - **画面・地図描画**: 本物のブラウザ (Playwright 等) で旧画面を開き、初期表示のズーム・中心座標、レイヤ表示、クリック時のポップアップ内容、コンソールエラー 0 件を記録する。
3. 追加した特性テストを旧ソフトウェア上で実行し、全件合格することを確認してコミットする。

### 2. 新環境へのテストの厳密な移植 (仕様の凍結)

1. 依存更新や全面作り直しで新しい環境・新リポジトリを作る場合、まず手順 1 で確定した特性テストと同一の入力・同一の期待ロジック・同一の境界値を持つテストを、新環境側のテストスイートとして先に書く。
2. この時点で新環境のテストは未実装のため落ちる (Red)。丸め誤差の許容 (例: 座標の小数桁、測地距離の 1 m 未満の差) が必要な場合は、勝手に緩めず「旧ソフトとの差異を許容する理由」を明記する。
3. 機能追加や意図的な仕様変更がある場合は、**「変えてはいけない互換テスト (旧ソフトと厳密一致)」** と **「新しく足す仕様のテスト」** を明確に別のテストケースとして分ける。

### 3. TDD (Red -> Green -> Refactor) での実装と移行

1. 新環境 (または改修ブランチ) で、移植したテストが 1 つずつ通るように実装を進める。
2. 依存関係マイグレーション (例: Leaflet 0.7 -> 1.9、Mapbox GL JS v1 -> MapLibre GL JS、OpenLayers 4 -> 10、PostGIS 2 -> 3) では、破壊的変更を 1 段階ずつ当て、各段階で特性テスト全件を通す。
3. 全面作り直しでは、Strangler Fig パターン (URL ルーティングや API エンドポイント単位で旧から新へ切り替える) と相性がよい。

### 4. 新旧突合 (Parity Check / Shadow Run)

- 同じテストデータセットとリクエスト群を旧ソフトウェアと新ソフトウェアの両方に流し、API JSON・GeoJSON 座標・検索件数・エラーコードが厳密に一致することを自動比較する。
- 意図しない差分が見つかった場合は、旧ソフトウェアの振る舞いを正本として新実装を直すか、旧側のバグであればプロダクト概要の「夜に決めたこと」に判断根拠を記録する。
