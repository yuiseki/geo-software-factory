# 試験を書くときの決まりと、不安定な試験

根拠は [sources](sources.md)。MapLibre の AGENTS.md と OpenLayers の試験の README は、エージェントや寄稿者が試験を書くときの決まりを明文化している。ここではそれを地図のプロダクトに合わせて書く。

## 試験を書くときの決まり

- 回帰の試験は、直す前に落ちることを確かめる。直す前に通る試験は、その不具合を守っていない。
- いちばん小さな試験のデータを使う。不具合を再現する最小の地物、最小のスタイル、最小のタイル。
- 同じことを二度確かめない。1 つの試験は 1 つのことを確かめる。
- 公開の API で試す。内部の状態を直に覗かない。
- 協力する部品を差し替え、試す部品は差し替えない。通信は自分の関数でなく、通信の層で差し替える。
- 試験を通すために、試験の期待値や許容を変えない。変えるときは、なぜ以前の期待が誤っていたかを、コミットに書く。
- 評価の環境を見分けて振る舞いを変える分岐を、本体に入れない。

## 落ちたとき

- まず、試験と試験のデータを疑う前に、本体の不具合かを確かめる。症状を最小にして、再現する試験を足す。
- 描画の比較で落ちたら、差分の画像を見る。許容を広げる前に、環境 (フォント、画素の比、ドライバー) の違いかを確かめる。環境の違いなら、その環境の期待の画像を足す (MapLibre は事例と環境ごとに複数の期待の画像を許す)。

## 不安定な試験

- 再試行は 1 回までにする。再試行のときは記録 (コンソール、通信、画面) を増やし、原因を追えるようにする (MapLibre)。
- 不安定な試験は、設定で隔離し、理由と担当と期限を書く (forge3d は走らせない試験の台帳に担当と期限を書く。deck.gl と CesiumJS は隔離した試験を手元では動かせるようにしておく)。期限が過ぎたら、直すか消すかを決める。
- 落ちると分かっている試験の一覧は、その試験が通るようになったら一覧の方を落とす。直ったことに気づけるようにする (mln-rs)。
- 隔離の一覧と、外した試験の理由を、朝の報告に入れる。

## 試験の仕組みそのものを確かめる

- 基準の画像を「実際の出力」として流し、比較の仕組みが一致と判定すること (mln-rs の自己検査)。
- わざと壊した版 (描画の層を外す、座標を入れ替える、認可の確認を外す) で、試験が落ちること。落ちないなら、その試験は守っていない (geo-software-eval の eval-of-eval と同じ考え方)。
- 期待値を作るスクリプトを作り直して、同じ期待値が出ること (RustGIS)。

## 速さの試験

- 速さの比較は、同じ計算機で、比べる 2 つを交互に (ABBA の順で) 何度も測り、統計で差を判定する (mln-rs のベンチマーク)。1 回ずつの測定で判定しない。
- 速さを CI の関門にするのは、測定が安定してからにする。調べた 6 つの Web の地図ライブラリは、どれも速さを関門にしていなかった (2026-11-13)。
