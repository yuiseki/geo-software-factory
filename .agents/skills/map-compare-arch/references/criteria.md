# 比較の軸 (アーキテクチャ)

後で書く (各 reference を埋めた後に書く)。

この文書に書く判断の軸:

- 地図プロダクトのアーキテクチャは、3 つの要素と 3 つの置き場所の組み合わせで決まる。
  - 要素: 保存 (データをどこに持つか)、計算 (選択、絞り込み、結合、変換、検索、経路計算をどこでするか)、表現 (タイル、JSON、画像など、どの形にしてどこで描くか)
  - 置き場所: クラウド、エッジ、ブラウザ・アプリ
- 機能 (タイル配信、検索、ルート検索、解析、正本と更新) ごとに、3 つの要素をどこに置くかを決める。正解は 1 つではなく、データの大きさ、転送時間、実行環境の制約、更新頻度、技術の進み具合で変わる。
- 書き込みの正本 (SSoT) と、読み出し用の成果物を分けて考える。正本は、遅くても強い整合性とトランザクションを優先して PostGIS や MongoDB などに置くことがある。読み出しは正本から作った成果物を、エッジやブラウザに配る。どこまでの遅れを許すかを要件から決める。
- 保存は段階で考える。ファイル (オブジェクトストレージや静的ホスティングに置くだけ、DB なし)、サーバーレスの DB、自前の API を持つ管理型 DB、高頻度の書き込みと購読に向くイベント型の保存、の順に重くなる。まずファイルで済まないかを確かめ、次の条件のどれかに当たったら一段上げる: 同じものへの同時の書き込み、端末に全件を落として絞り込めない量と複雑さ、1 件だけの部分更新、サーバー側で強制するアクセス制御 (行単位の出し分け)、参照の整合性、サーバー側の集計、監査と履歴、変更の即時の通知、サーバー側でのルールの強制。
- 信頼の境界で計算の置き場所が決まる。ブラウザ・アプリは利用者の手元にあり、改ざんされうる。アクセス制御、不正の防止 (位置の偽装、得点、ポイント、決済)、正解の判定のような、ルールを強制する計算はブラウザに置けない。逆に、公開してよいデータの絞り込みや表示はブラウザに寄せられる。
- 地図は簡単でも、動的な地図はバックエンドの問題になる。表示の部品はそろっていても、書き込み、認証と権限、即時の通知、配備を足すと、地図とは別の構成要素が要る。認証を、置き場所と同じ表の上で一緒に決める。
- ロックインを置き場所ごとに見る。認証や行単位のアクセス制御が特定の BaaS の独自関数に結びつくと、正本を移しにくくなる。標準の PostgreSQL や OSS の認証のような逃げ道があるかを書く。
- 費用は 1 回の表示あたりの単価だけでなく、限界費用で見る。小さな地図アプリを多数作る場合は、無料枠に収まるかが効く。ファイルで配る構成では、1 回の表示で発生するリクエストの数 (PMTiles の Range 取得など) に課金されるので、表示回数で課金されるサービスより高くなることもある。
- ブラウザを表示の場所としてだけ見ない。Service Worker、OPFS、Wasm、WebGPU などで、保存と計算もブラウザに置けるかを、最初に検討する。
