# AI で集めた、AI で確かめたデータ

対象: AI エージェントが Web の公式サイト、SNS、記事を読んで集めた、または既存の一覧 (OSM など) の項目ごとに確かめたデータを、地図に載せるときの記録、表示、抜き取り検査、ライセンスの扱い

## メタ情報

| 項目 | 値 |
|---|---|
| 確かめた日 | 2026-11-11 |

## 概要

2026-11-11 の観察では、今からほんやが全国 8,673 店の書店の一覧を、AI (Claude) に各店の公式サイト、SNS、記事を確かめさせて作り、人が確かめていないことをデータに書き、出典を © OpenStreetMap contributors (ODbL) としていた。AI で集めると、人手では届かない件数を短い時間で揃えられるが、誤りの率が分からないまま地図に載り、元のサイトの条件と OSM の ODbL の条件が見えにくくなる。この文書は、地図に載せる前に何を記録し、どう見せ、どれだけ確かめ、ライセンスをどう扱うかをまとめる。AI の出力の扱いそのものを定めた公的な指針や OSMF の公式見解は見つけていないので、条文や公式ガイドラインから読めるもの以外は推奨 (推測) として書く。

## 記録すること (推奨)

項目ごとに、次の列をデータそのものに持たせる。地図の上で見せる元にもなる。

- 集め方: `method` (例: `ai_web_check`、`ai_extracted`、`human_survey`、`osm_as_is`)。
- 確かめた日: `checked_at` (日付)。営業の有無や営業時間は変わるので、日付の無い「確認済み」は使わない。
- 根拠の URL: AI が読んだページの URL を項目ごとに残す。根拠の無い値は、AI が作った値として扱う。
- 人の確認: `human_verified` (yes / no) と、確かめた人の役割と日付。
- 使ったモデルと手順: データ全体の説明 (README やデータのページ) に、モデルの名前と版、指示の要点、実行した期間を書く。項目ごとでなくてよい。
- 元の一覧: OSM などを出発点にしたなら、その抽出の日時と条件 (例: `shop=books` の日本全体、2026-11-01 の planet)。

## 地図の上で見せること (推奨)

- 人が確かめていない項目は、記号か凡例で分かるようにする (例: 枠線を点線にする、ポップアップに「AI が Web の情報から確かめた (人は未確認)、確かめた日 2026-11-01」と書く)。
- データ全体の注記に、集め方、確かめた期間、抜き取り検査の結果 (下の節) を書く。件数だけを大きく見せない。
- 誤りを知らせる手段 (フォームや Issue) を付け、直した日を残す。
- 安全に関わる情報 (避難場所、医療機関の診療の有無など) は、AI で確かめただけの値を出さない。公的な出どころか人の確認に限る。

## 抜き取り検査 (推奨)

公開の前に、一様に無作為に選んだ標本を人が元のページや現地と突き合わせ、誤りの率を出す。便宜の標本 (目についた店、近所の店、AI が自信ありとした店) は偏るので使わない。

- 誤りの定義を先に決める: 存在しない、閉店、位置が違う (例: 100m 以上)、名前が違う、など。項目ごとに数える。
- 標本の大きさの目安: 100 件で誤り 0 件なら、誤りの率の 95% 区間の上限は約 3.7% (Wilson の区間)。100 件中 5 件なら 2.2〜11.2%。誤りの率を ±5 ポイントで言いたいなら約 385 件 (1.96² × 0.25 / 0.05²)。385 件で 0 件なら上限は約 1.0%、19 件なら 3.2〜7.6%。数値は区間の式からの計算で、どの大きさが十分かは用途で決める。
- 報告の形: 「無作為に選んだ n 件を人が確かめ、k 件 (k/n) に誤り、95% 区間 a〜b%。誤りの定義は ...、確かめた日 ...」。誤りの種類ごとの内訳も書く。
- 地域や種類で質が違いそうなら、層 (都道府県、チェーン店か個人店か) ごとに抜き取り、層ごとの率を書く。
- 検査で見つけた誤りを直したあと、同じ標本で率を測り直さない。直した標本は誤りが減って見えるので、測り直すなら新しい無作為の標本を取る。

## ライセンスの扱い

AI を通しても、元のデータの条件は消えない。

- サイトの利用規約: 公式サイトや店舗検索から写した値は、そのサイトの利用規約 (契約) の対象のままと考える (推測)。規約が転載や機械的な取得を禁じていれば、AI に読ませても同じ。AllThePlaces の CC0 と各社のサイトの規約の関係も未確認のまま ([alltheplaces](sources/alltheplaces.md))。
- 著作権法: 第 12 条の2 は「データベースでその情報の選択又は体系的な構成によつて創作性を有するものは、著作物として保護する」と定める。個々の事実 (住所、営業時間) より、店舗の一覧の選び方や組み立てごと写すことのほうが問題になりうる (推測)。説明文や写真を写すのは、それぞれの著作物の問題になる。
- SNS と記事: 投稿や記事の文章、写真を地図に載せない。AI に要約させた文も、元の表現に近ければ同じ扱いになりうる (推測)。事実 (営業中か、移転先) だけを取り、根拠の URL を残す。
- 混ぜた結果の条件: 条件の違う出どころ (CC0、CC BY、サイトの規約、ODbL) から集めた値を 1 つのデータにするなら、項目ごとに出どころを残し、[license-mixing](license-mixing.md) で一番重い条件を確かめる。

## OSM を出発点にしたとき

- OSM の一覧 (例: `shop=books`) を取り出し、項目ごとに AI で確かめて値を直し、足したデータは、OSM を改変したデータベース (ODbL の派生データベース) になる。公に使うなら ODbL (または互換) で出し、派生データベースか変更点を提供する申し出が要る (ODbL 4.4、4.6、[license-mixing](license-mixing.md))。地図の隅に © OpenStreetMap contributors を書くだけでは足りない。
- 同じ種類の地物 (書店) を OSM と AI の集めた店で補い合うと、別のレイヤーにしても共有義務がかかる (OSMF の Horizontal Map Layers ガイドライン)。
- OSM を出発点にせず、AI だけで集めたデータには OSM の条件はかからない。その場合、そのデータに OSM の出典を付けると出どころを誤解させる。OSMF の Attribution Guidelines は、OSM を使っていない範囲や地物では OSM の表示を出さないほうが望ましいとしている ([license-mixing](license-mixing.md))。
- サイトの規約が再配布を禁じる値は、ODbL で出す派生データベースに入れられない (推測)。入れるなら、その値を外すか、提供者に許諾を取る。
- 直した値を OSM に書き戻すなら、自動編集の行動規範に従う: 事前に計画を wiki に書いて議論し、変更セットに `mechanical=yes` (または `bot=yes`) を付ける (https://wiki.openstreetmap.org/wiki/Automated_Edits_code_of_conduct)。投稿者は、他人の知的財産権を侵さず、OSMF に使わせる権利があることを表明する (Contributor Terms 1(a))。AI の出力を OSM に入れることについての OSMF の公式見解は見つけていない (未確認)。
