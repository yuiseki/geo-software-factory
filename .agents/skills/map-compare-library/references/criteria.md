# 比較の軸 (地図ライブラリ・SDK)

描画ライブラリ、ネイティブ SDK、クロスプラットフォームのライブラリ、地図アプリの土台、抽象化層を、同じ軸で並べるための手順。比較を始める前に読む。各候補の事実は `libraries/`、`native/`、`cross-platform/`、`frameworks/`、`multi-sdk/`、`niche.md` にあり、この文書には軸と判定の手順だけを書く。例として挙げる事実は、各 reference に 2026-11-10 時点で書かれていたもの。

## 進め方

1. 要件 (プロダクト概要) から、対象端末と、使うタイル・地図データの供給元を確かめる。供給元が決まっていなければ、先に map-compare-infra で決めるか、両方を並行して決める (「タイルの供給元との関係」の節)。
2. 足切りの条件で候補を減らす。足切りは「点数を下げる」ではなく「候補から外す」。
3. 残った候補を、評価の軸ごとに比べる。軸の重みは「要件から軸の重みを決める」の表で決める。
4. 推奨を先に書き、続けて軸と候補ごとの評価を表で示す。確かめられなかった項目は「未確認」のまま表に残し、推測で埋めない。

## 足切りの条件

| 条件 | 何を確かめるか | 外れる例 (各 reference の記述) |
|---|---|---|
| 対象端末 | Web、Android、iOS、デスクトップ、ゲームエンジン、組み込み機器のどれで動かすか | react-native-maps は Web に対応しない ([react-native-maps](cross-platform/react-native-maps.md))。組み込み・車載は MapLibre Native Qt などに限られる ([niche](niche.md)) |
| タイルの供給元との組み合わせ | 使うタイルを、そのライブラリで表示してよいか | Mapbox のタイルはモバイルでは Mapbox の SDK を通してしか使えない。Geolonia Maps のタイルは Geolonia Maps SDK を通して使う ([geolonia-maps](libraries/geolonia-maps.md))。Google のタイルは Google 以外の地図と併用できない。ArcGIS Maps SDK for JavaScript は Web で使う場合に他の Esri 製品との併用が求められる ([arcgis-maps-sdk-js](libraries/arcgis-maps-sdk-js.md)) |
| ライセンス | プロダクトの配布形態 (SaaS、アプリのストア配布、受託納品、OSS 公開) と、ライブラリと主要な依存のライセンスが両立するか | maptalks.js の 3D 系パッケージは UNLICENSED ([maptalks](libraries/maptalks.md))。flutter_map のオフライン用に推奨される flutter_map_tile_caching は GPL-3.0 ([flutter-map](cross-platform/flutter-map.md))。react-leaflet は OSI 非承認の Hippocratic License ([leaflet](libraries/leaflet.md)) |
| 必須の描画能力 | ベクトルタイル、3D 建物、地形、地球儀、3D Tiles のうち、要件で欠かせないもの | Leaflet は本体だけではベクトルタイルとスタイル仕様を扱えない ([leaflet](libraries/leaflet.md))。3D Tiles が要るなら、CesiumJS、3DTilesRendererJS、ゲームエンジン向けの Cesium などに限られる |
| 利用料 | ライブラリ自体に利用料や課金があるか | Mapbox GL JS は v2 以降が独自ライセンスで、地図ロードで課金される ([mapbox-gl-js](libraries/mapbox-gl-js.md)) |

## 評価の軸

### 1. 描画の能力

- 描画方式: DOM、Canvas 2D、WebGL、WebGPU。描画できる地物の数と、拡大縮小やアニメーションの滑らかさに効く。
- ラスタとベクトル: ベクトルタイルを描けるか、スタイル仕様 (MapLibre Style Spec など) で配色や表示を変えられるか。
- 2D、2.5D (傾きと回転)、3D: 建物の立ち上げ、地形、地球儀、3D Tiles。
- 投影法: Web メルカトル以外 (地球儀、極域、独自の平面座標) が要るか。
- 新しいタイル形式への追随: MLT (MapLibre Tile) などへの対応。

### 2. 性能と規模

- 表示できる地物の数の目安。公式の記述がない場合が多いので、要件の件数で試作して測る。
- バンドルサイズ。Web では初期表示の速さに効く。ライブラリによっては依存 (three.js など) を含むか含まないかで値が大きく変わる (globe.gl は three.js を含む、[globe-gl](libraries/globe-gl.md))。
- 低性能端末とモバイルブラウザでの挙動。
- 大量データの可視化が中心なら、地図ライブラリに deck.gl などの可視化レイヤーを重ねる構成も候補にする ([deck-gl](libraries/deck-gl.md))。

### 3. 対象端末と開発環境への統合

- Web のフレームワーク (React、Vue など) 向けのラッパーがあるか、そのラッパーが保守されているか、ライセンスは何か。
- モバイル: ネイティブ (Jetpack Compose、SwiftUI)、React Native、Flutter のどれで作るか。クロスプラットフォームのライブラリは、自前で描画するもの (flutter_map) と、OS や他社の SDK を包むもの (react-native-maps) で、規約と課金の引き継ぎ方が違う。
- Web とネイティブで同じスタイルを使いたいか。MapLibre GL JS と MapLibre Native は同じスタイル仕様を使える。
- ゲームエンジン、.NET、組み込み機器への対応。

### 4. ライセンスと費用

- ライセンスの種類: 寛容な OSS (MIT、BSD、Apache-2.0)、弱いコピーレフト (LGPL、MPL)、強いコピーレフト (GPL、AGPL)、OSI 非承認、商用製品。
- 配布形態ごとの義務: SaaS として提供する、アプリをストアで配布する、受託で納品する、改変して配る、のそれぞれで何が求められるかを、各 reference の「ライセンス上の注意」で確かめる。
- 主要な依存とプラグインのライセンス: 本体が寛容でも、推奨されるプラグインがコピーレフトのことがある。
- 版によるライセンスの変化: Mapbox GL JS は v1 系が BSD-3-Clause、v2 以降が独自ライセンス。OpenGlobus は版によって MIT と Apache-2.0 が分かれる ([openglobus](libraries/openglobus.md))。
- ライブラリ自体の利用料: OSS は無料でも、組み合わせる SDK やタイルの課金は別にかかる。

### 5. 成熟度と保守体制

- 運営主体: 財団や中立な組織 (MapLibre、OSGeo、OpenJS Foundation)、単一の企業、個人。個人や少人数で保守されているものは、保守が止まったときの影響を見込む (globe.gl は個人の保守、MapConductor はコアのコミットが 1 人に集中している、[mapconductor](multi-sdk/mapconductor.md))。
- 開発の活発さ: 直近 1 年のリリース数、最終コミット日、未解決の不具合の扱い。
- 破壊的変更: 大きな版の移行中かどうか (Leaflet は 2.0 が beta の段階で、ラッパーの対応は未確認、[leaflet](libraries/leaflet.md))。新しい描画方式の本番利用が勧められているか (deck.gl は WebGPU の本番利用をまだ勧めていない)。
- 情報の量: 公式ドキュメント、日本語の情報、利用例。

### 6. 移行のしやすさ

- スタイル仕様の互換: MapLibre Style Spec で書いておけば、MapLibre 系のライブラリの間で使い回せる。
- タイルの供給元を替えたときに、ライブラリも替える必要があるか。独自 SDK でしか表示できないタイルを選ぶと、ライブラリも固定される。
- 抽象化層: 地図 SDK を将来乗り換える、または複数の SDK を併用する見込みがあるなら、MapConductor などの抽象化層を挟むかを検討する。共通 API に無い機能は SDK ごとに書くことになるので、要件の機能が共通 API に入っているかを確かめる ([mapconductor](multi-sdk/mapconductor.md))。

### 7. 作らずに済ませる選択肢

ライブラリから組む代わりに、地図アプリの土台 (TerriaJS、Re:Earth Visualizer、kepler.gl) を使うと、レイヤー一覧、凡例、データの読み込みなどが最初から手に入る。代わりに画面の作りや機能の拡張に限界がある。要件の機能が土台の機能に収まるか、収まらない部分を拡張で足せるかで比べる (`frameworks/` の各 reference)。

### 8. 特殊な要件

屋内地図、完全オフライン、組み込み機器、地理座標を持たない巨大画像 (フロアプラン、ゲームマップ)、印刷や PDF の出力が要件に入っていれば、[niche](niche.md) から候補を足す。

## タイルの供給元との関係

ライブラリとタイルの供給元は互いに制約する。次の順で決める。

1. 供給元が要件で決まっている (既存契約、公共案件で公的データを使う、など) なら、その供給元を表示してよいライブラリだけを候補にする。
2. ライブラリが要件で決まっている (既存のアプリ、社内の標準) なら、そのライブラリで表示してよい供給元だけを map-compare-infra の候補にする。
3. どちらも決まっていなければ、移行のしやすさを重く見て、スタイル仕様が共通の組み合わせ (MapLibre 系のライブラリと、MapLibre Style Spec で配信される供給元) を基準にし、そこから外れる組み合わせを選ぶ理由 (独自の機能、データの詳しさ) を書く。
4. 同じ供給元でも、ライブラリによって課金単位が変わる。Mapbox と MapTiler は、自社の SDK を使うと地図の表示回数で、MapLibre などから直接タイルを取るとタイルのリクエスト数で課金される。ライブラリの選択を費用の見積もりに反映する (map-compare-infra の criteria.md の「費用の見積もり方」)。

## 要件から軸の重みを決める

| 要件 | 足切りに当てる条件 | 重くする軸 |
|---|---|---|
| マーカーを少し置くだけの Web 地図 | 対象端末 | 性能と規模 (バンドルサイズ)、成熟度と保守体制 |
| 大量の地物、ベクトルタイル、配色の作り込み | 必須の描画能力 | 描画の能力、性能と規模 |
| 3D 都市、地形、地球儀 | 必須の描画能力 | 描画の能力、性能と規模 |
| スマートフォンのアプリ | 対象端末、タイルの供給元との組み合わせ | 対象端末と開発環境への統合、ライセンスと費用 (ストア配布) |
| Web とアプリで同じ見た目 | 対象端末 | 対象端末と開発環境への統合、移行のしやすさ |
| 受託開発で納品する、OSS として公開する | ライセンス | ライセンスと費用、成熟度と保守体制 |
| 長く保守する業務システム | なし | 成熟度と保守体制、移行のしやすさ |
| 早く出したい、開発の人手が少ない | なし | 作らずに済ませる選択肢 |
| 屋内、オフライン、組み込み、印刷 | 対象端末 | 特殊な要件 |

## この文書で扱っていない軸

- アクセシビリティ (スクリーンリーダーでの操作、キーボード操作、配色のコントラスト): reference で調べていない。要件に入っていれば、候補ごとに公式ドキュメントと実装を確かめる。
- セキュリティ (依存の脆弱性の扱い、CSP との相性): reference で調べていない。
