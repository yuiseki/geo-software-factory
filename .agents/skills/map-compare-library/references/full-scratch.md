# full-scratch (ライブラリを使わずに描画器を書く)

既存の地図ライブラリや SDK に頼らず、その依頼のためだけの描画器を書く選択肢。Canvas 2D、WebGL2、WebGPU、SVG、ネイティブの描画 API (OpenGL ES、Metal、Vulkan)、マイコンの画面のバッファなどに、投影、データの読み込み、描画、操作を直接書く。

コーディング AI エージェントを使えば、投影の式、タイルの番号の計算、ベクトルタイルの復号、三角形分割、当たり判定といった部品は、公開された仕様から短い時間で書ける。そのため、フットプリントや性能を極端に重く見る要件では、現実的な候補になる。ただし、汎用のライブラリが代わりに払っている手間 (下の「自分で持つことになるもの」) は、そのまま自分の側に移る。

## 向いている場面

- 要件が 1 つに絞られていて、機能が少ない。例: パン・ズームしない主題図、投影が固定された 1 枚の図、決まったデータを 1 種類だけ描く、選ぶ・当てるだけの操作。
- コードの大きさ、起動時間、メモリ、1 フレームの時間に、厳しい上限 (予算) がある。例: 記事やメールに埋め込む軽い地図、低性能の端末やモバイル回線での表示、何度も開かれる画面。
- 汎用のライブラリが動かない、または載らない場所で描く。例: マイコンや組み込み機器の小さな画面、ゲームエンジンや独自の描画系の中。[niche](niche.md) の候補でも合わないとき。
- 汎用のライブラリが前提にしているものと要件がずれる。例: Web メルカトル以外の投影、地理座標を持たない画像、データ量に合わせた独自のデータ形式。
- 依存を増やしたくない。例: 供給網の攻撃面を減らしたい、長く凍結して配りたい、ライセンスを自分のものだけにしたい。

## 向いていない場面

- ベースマップ全体 (道路、建物、多数の地名のラベル) をスタイル付きで描く。スタイル仕様、ラベルの配置と衝突の回避、文字の描画を作り直すことになり、汎用のライブラリとの差が小さくなる。
- 要件が増え続ける、どこまで増えるか分からない。機能を足すたびに、汎用のライブラリを自分で作り直す方向へ進む。
- 3D Tiles、地形、地球儀など、仕様が大きく、精度の扱いが難しい形式を、要件どおりの品質で描く必要がある。
- アクセシビリティ (キーボード操作、スクリーンリーダー) の要件が厳しい。
- 書いたコードを読める人やエージェントが、保守の期間を通していない。

## 自分で持つことになるもの

汎用のライブラリなら最初から入っているが、full-scratch では要件に入っている分だけ自分で書いて確かめるもの。要件に入っていないものは書かない。それが full-scratch の利点になる。

- 投影と座標: 投影の式、タイルの番号、高解像度の画面 (devicePixelRatio)、日付変更線と極、浮動小数点の精度。
- データの読み込み: タイルや Range で読む形式 (Mapbox Vector Tile、PMTiles、GeoJSON など) の復号、キャッシュ、読み込み中と失敗の表示。
- 描画: ポリゴンの三角形分割、線の太さと継ぎ目、描画の順序、WebGL のコンテキストの喪失からの復帰。
- 文字: 日本語を含む文字の描画、ラベルの配置と重なりの回避。Canvas 2D の文字描画を使えばブラウザに任せられるが、WebGL や WebGPU ではグリフの用意から自分で持つ。
- 操作: ドラッグ、ホイール、ピンチ、慣性、当たり判定。マウスとタッチの両方。
- 帰属表示: 地図データとタイルの帰属表示 (OpenStreetMap の ODbL の表示、タイルの供給元の表示) を、規約どおりに自分で出す。ライブラリの帰属表示の部品は使えない。
- テストと確かめ方: 描いた結果が正しいかを、画面のピクセルや目視で確かめる手順。数値の予算を通っても、間違った地図を描いていることがある。

## 組み合わせの制約

- タイルの供給元の規約が、特定の SDK を通して使うことを求めていると、full-scratch では使えない。Google のタイルは Google 以外の地図と併用できず、Mapbox のタイルはモバイルでは Mapbox の SDK を通してしか使えない ([mapbox-maps-sdk](native/mapbox-maps-sdk.md))。Geolonia Maps のタイルは Geolonia Maps SDK を通して使うのが推奨で、他のライブラリから使うのはサポート外 ([geolonia-maps](libraries/geolonia-maps.md))。full-scratch を選ぶなら、規約が直接の取得を許す供給元か、自前で配るデータ (map-compare-infra、map-compare-arch) と組む。
- スタイル仕様 (MapLibre Style Spec など) とは互換にならない。スタイルを使い回す、後で汎用のライブラリへ移る見込みがあるなら、移行の手間に数える。

## ライセンス上の注意

- 自分で書いたコードのライセンスは自分で決められる。依存を持たなければ、依存のライセンスの確認も要らない。
- エージェントに既存のエンジンの実装を読ませて移すと、元のライセンスが及ぶことがある。GPL などのコピーレフトのエンジンからコードや細かい設計を移すと、成果物の配布に条件が付く。仕様 (Mapbox Vector Tile の仕様、PMTiles の仕様、投影の式) と、寛容なライセンスの資料から書く。どこを読んで書いたかを残す。
- 地図データとタイルのライセンス (ODbL の継承条件、帰属表示) は、描画器の作り方と関係なく残る (map-compare-data、map-legal-check)。

## 性能と規模

- 汎用のライブラリより小さく速くなるのは、要件に要らない機能を持たないからで、書けば必ず速くなるわけではない。速いと言うには、同じ依頼を汎用のライブラリでも作り、同じデータ、同じ画面、同じ操作で測って並べる (map-poc-measure)。
- 投影、簡略化、三角形分割、並べ替えを、描画のたびでなく、データを用意するときに済ませておくと、描画器のコードと 1 フレームの仕事が減る。代わりにデータの形が描画器と結び付き、データを替えると描画器も直すことになる。
- 予算は数値で決める。例: 配るコードの大きさ (gzip 後)、初回描画までの時間、1 フレームの時間、メモリ。予算を決めずに作り始めると、汎用のライブラリとの違いが言えない。

## 比べ方

1. 要件から、full-scratch で書くものの一覧 (上の「自分で持つことになるもの」のうち要件に入るもの) を作る。一覧が長いなら、汎用のライブラリを選ぶ。
2. タイルの供給元の規約が、直接の取得を許すかを確かめる。許さなければ外す。
3. 予算を数値で決め、同じ依頼の汎用のライブラリ版を比べる相手として作る。
4. 試作して両方を同じ条件で測る。予算を満たし、汎用のライブラリとの差が要件に効くときだけ推奨する。
5. 推奨するときは、保守の期間に誰が (どのエージェントが) コードを読んで直すか、要件が増えたら汎用のライブラリへ移るかの線を、答えに書く。
