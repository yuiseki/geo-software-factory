# full-scratch (ライブラリを使わずに描画器やエンジンを書く)

既存の地図ライブラリや SDK に頼らず、描画器や地図エンジンを自分で書く選択肢。Canvas 2D、WebGL2、WebGPU、ネイティブの描画 API、マイコンの画面のバッファなどに、投影、データの読み込み、描画、操作を直接書く。

コーディング AI エージェントを使えば、規模は 2 通りある。

- 依頼専用の描画器: 1 つの依頼に要る機能だけを持つ、小さな描画器。
- 自前の地図エンジン: 既存のスタイル仕様や API と互換を持ち、ベクトルタイルとラベル、3D の建物、地形、地球儀、点群、3D Tiles までを描く汎用のエンジン。

後者も、少人数とエージェントで、数週間から数か月で作られた例がある。ブラウザや OS の違い (iOS の WebKit や Android の GPU ドライバの不具合など) を実機で確かめて直し、既存のライブラリの公式の作例を互換の基準にして採点している。技術的にできるかどうかは、もう選定の分かれ目にならない。分かれ目は、エンジンを持ち続ける仕事を引き受けるかどうかにある。

## 汎用のライブラリが引き受けているもの

汎用のライブラリを選ぶ理由は、描画のアルゴリズムではなく、次の仕事を引き受けてくれることにある。full-scratch では、これを自分で引き受ける。エージェントはこれらもこなせるが、一度作れば終わる仕事ではなく、製品の寿命を通して続く仕事になる。

- ブラウザの違い: ブラウザごとの仕様の実装の差、挙動の差、版による変化への対応。
- OS やプラットフォームの違い: OS、端末、GPU とそのドライバ、画面の解像度、メモリの上限、入力機器ごとの挙動の差への対応。
- 操作の網羅: ドラッグ、ホイール、ピンチ、回転、慣性、キーボード、マウスとタッチとペンの混在、ページのスクロールとの両立など、膨大な操作の組み合わせと、それが環境ごとにどう違うかへの対応。
- 細かいエッジケースのバグ: 日付変更線や極、浮動小数点の精度、GPU のコンテキストの喪失、読み込みの失敗や再試行、極端なデータなど、まれな条件で起きる不具合の発見と修正。
- 継続的な保守: ブラウザ、OS、端末、データ形式、セキュリティの要求 (CSP など) といったエコシステムの変化に、公開したあとも追随し続けること。

## 向いている場面

- フットプリントや性能を極端に重く見る。配るコードの大きさ、起動時間、メモリ、1 フレームの時間に厳しい予算がある。汎用のライブラリの数分の 1 の大きさで、同じスタイルの地図を描くエンジンも作れる。
- 汎用のライブラリが前提にしているものと要件がずれる。例: Web メルカトルを使わない (地球儀を基本にする、正積図法で描く)、地理座標を持たない画像、データ量に合わせた独自のデータ形式やタイル形式。
- 汎用のライブラリが動かない、または載らない場所で描く。例: マイコンや組み込み機器の小さな画面、独自の描画系の中。
- 地図エンジンそのものを、自分たちの製品として持つと決めている。既存のライブラリとの互換を保ちながら、独自の機能や性能で差を作る。
- 依存を増やしたくない。例: 供給網の攻撃面を減らしたい、ライセンスを自分のものだけにしたい。

## 向いていない場面

- 作ったあと、実機での確かめと不具合の修正と追随を、製品の寿命を通して続ける体制が無い。上の「汎用のライブラリが引き受けているもの」が、誰の仕事にもならなくなる。
- 対象のブラウザ、OS、端末を実機で確かめる手段が無い。自動テストが 1 つのブラウザでしか回らないなら、ほかのブラウザでの挙動は未確認のまま残る。
- 汎用のライブラリで要件が満たせていて、フットプリント、性能、独自の表現のどれにも差を作る理由が無い。

## 進め方

1. 規模を決める。依頼専用の描画器か、自前の地図エンジンか。後者なら、エンジンを持ち続ける体制 (誰が、どのエージェントが、実機での確かめと追随を続けるか) を先に決める。
2. 予算を数値で決める。配るコードの大きさ (gzip 後)、初回描画までの時間、1 フレームの時間、メモリ。予算を決めずに作り始めると、汎用のライブラリとの違いが言えない。
3. 互換の基準を決める。既存のスタイル仕様 (MapLibre Style Spec など) や API の一部と互換にすると、既存のスタイル、タイル、コード、エージェントの知識を使い回せ、汎用のライブラリへの切り戻しもしやすい。対応しない機能は一覧にし、読み込んだときに警告を出す。
4. 互換を採点する。既存のライブラリの公式の作例を同じ入力で動かし、同じ絵になるか、同じ答えを返すかを数える。採点の結果を公開すると、利用者が足りるかを自分で判断できる。
5. 実機で確かめる。対象の各ブラウザ、OS、端末で、描画、操作、メモリの上限を確かめる。GPU や描画 API が使えない環境への切り替え (WebGPU から WebGL2 へ、自前のエンジンから汎用のライブラリへ) を用意する。確かめていない環境は、確かめていないと書く。
6. 汎用のライブラリと同じ条件で測る。同じデータ、同じ画面、同じ操作で両方を測り、計測の手順をリポジトリに置いて、誰でも再現できるようにする (map-poc-measure)。

## 組み合わせの制約

- タイルの供給元の規約が、特定の SDK を通して使うことを求めていると、full-scratch では使えない。Google のタイルは Google 以外の地図と併用できず、Mapbox のタイルはモバイルでは Mapbox の SDK を通してしか使えない ([mapbox-maps-sdk](native/mapbox-maps-sdk.md))。Geolonia Maps のタイルは Geolonia Maps SDK を通して使うのが推奨で、他のライブラリから使うのはサポート外 ([geolonia-maps](libraries/geolonia-maps.md))。full-scratch を選ぶなら、規約が直接の取得を許す供給元か、自前で配るデータ (map-compare-infra、map-compare-arch) と組む。
- 帰属表示: 地図データとタイルの帰属表示 (OpenStreetMap の ODbL の表示、タイルの供給元の表示) は、ライブラリの部品を使わずに、規約どおりに自分で出す。

## ライセンス上の注意

- 自分で書いたコードのライセンスは自分で決められる。
- エージェントに既存のエンジンの実装を読ませて移すと、元のライセンスが及ぶことがある。GPL などのコピーレフトのエンジンからコードや細かい設計を移すと、成果物の配布に条件が付く。仕様 (Mapbox Vector Tile の仕様、PMTiles の仕様、スタイル仕様、投影の式) と寛容なライセンスの実装から書き、移した部分と元のライセンスの表示を残す (BSD や ISC の実装を移したら、その著作権表示を同梱する)。
- 地図データとタイルのライセンス (ODbL の継承条件、帰属表示) は、描画器の作り方と関係なく残る (map-compare-data、map-legal-check)。
