# 地図の段階的な切り替えの手順

対象: 移行の範囲の洗い出し、機能の対応表、一部の画面や利用者からの切り替え、比較の方法、戻し方

## メタ情報

| 項目 | 値 |
|---|---|
| 確かめた日 | 2026-11-11 |

## 概要

地図の乗り換えは、ライブラリのコード、地図データ、検索やルート検索の API、保存しているデータ、帰属表示、費用が同時に変わる。一度に全部を切り替えると、問題が出たときに何が原因か分からず、戻すのも難しい。この文書は、移行の範囲を洗い出し、移行元の規約が許す単位で少しずつ切り替え、比べて、戻せるようにしておく手順をまとめる。各手法は一般的なソフトウェアの切り替えの手法で、地図に固有の制約 (規約による併用の禁止、データの持ち越しの禁止) を重ねて書く。

## 手段

| 手段 | 何が解決するか | 制約 | 対応するライブラリ・サービス (版) | 出典 |
|---|---|---|---|---|
| 地図の抽象化層 (自社のラッパー) | 画面のコードから地図ライブラリを切り離し、移行元と移行先を同じ呼び出しで切り替えられる | 両方のライブラリに共通する機能しか包めない。包む範囲を広げすぎると移行より手間がかかる | 自作、または MapConductor ([mapconductor](../../map-compare-library/references/multi-sdk/mapconductor.md)) | 一般的な手法 |
| 機能フラグ (feature flag) | 画面、利用者、地域ごとに移行先を出すかを、配布し直さずに切り替える。戻しも同じフラグで行う | Google の地図から移るときは、同じ画面で両方を出せない。フラグの単位を画面か利用者にする ([from-google-maps](from-google-maps.md)) | 自作か、既存のフラグ配信サービス | 一般的な手法 |
| 段階的な公開 (カナリア) | 少数の利用者から出し、エラー率、地図の読み込み時間、問い合わせを見て広げる | ネイティブアプリはストアの段階的な公開に従い、配布した版は戻せない。フラグで新旧を両方入れておく | アプリストアの段階的な公開、Web は配信の設定 | 一般的な手法 |
| A/B 比較 | 利用者の行動 (検索の成功、目的地への到達、離脱) を新旧で比べる | 地図の見た目の差は好みで評価が割れる。測る指標を先に決める。移行元の規約が併用を禁じるなら、同じ利用者に両方を見せない | 分析基盤 (計測の設計は map-poc-measure、運用は map-ops) | 一般的な手法 |
| 並べての目視比較 (スクリーンショット) | 代表的な場所とズームで、新旧の見た目の差を見落とさない | 移行元の地図のスクリーンショットを保存して配ることは規約で禁じられることがある (Mapbox は地図コンテンツの保存を原則禁止、Product Terms 1.9)。社内の比較に限り、保存の扱いを確かめる (未確認) | ヘッドレスブラウザ (Playwright など) | 一般的な手法、[mapbox](../../map-compare-infra/references/providers/mapbox.md) |
| 影の呼び出し (shadow) | 検索とジオコーディングで、同じ入力を移行先にも投げて結果を比べる | Google の検索結果を他社の地図に出さない、保存しない。結果の比較は件数や距離などの集計にとどめる (推測。規約の読み方は [from-google-maps](from-google-maps.md)) | 自作 | 一般的な手法 |

## 判断を左右すること

- 移行元の規約が、併用とデータの持ち越しを許すか。Google は他社の地図との併用とキャッシュをほぼ許さず、Mapbox はモバイルで Mobile SDK 以外からのアクセスを許さない ([api-terms](../../map-legal-check/references/api-terms.md))。これで切り替えの単位 (画面ごと、利用者ごと、一斉) が決まる。
- 移行元の契約の終わり方。年間契約の更新日、解約の通知期限、終了後に削除するもの (Google は契約終了の日までにサービスのコンテンツを削除する、利用規約 10.6(c)、https://cloud.google.com/maps-platform/terms)。移行の最終日はここから逆算する。
- Web かネイティブアプリか。Web は配信の切り替えですぐ戻せる。ネイティブアプリは古い版が残るので、移行元の API キーを止める日を、古い版の利用者の割合を見て決める。
- 保存しているデータのうち、移行元に由来するもの (座標、place_id、ジオコーディングの結果) の量。付け直しの費用と時間が移行の期間を決める。
- 移行の理由。費用なら新旧の費用を同じ規模で並べ、機能なら移行先で失う機能を先に並べる。移行で失うものが理由より大きいなら、移行しない結論もありうる。

## 手順

1. 棚卸し: 今の地図が使っているものを、下の項目ごとに書き出す。数はコードの検索とアクセスログ、請求書から取る。
   - 描画: ライブラリと版、地図を出す画面の一覧、スタイル (誰が作ったか、どこにあるか)、マーカー、図形、クラスタ、ヒートマップ、3D、地形
   - データ: タイルの供給元、検索 (ジオコーディング、POI、オートコンプリート)、ルート検索、ストリートビュー、静的地図の画像
   - 保存: キャッシュ、オフライン、DB に保存している座標や ID、その出どころ
   - 計測: 地図の利用の分析、移行元の SDK が送るテレメトリ
   - 費用と契約: 月の地図表示回数、API ごとの呼び出し回数、契約の更新日
   - 表示: 帰属表示の文言と位置
2. 移行元の規約で、持ち越せないものと併用できないものに印を付ける (from-google-maps、from-mapbox、from-leaflet-raster の「規約上の注意」)。
3. 移行先を選ぶ: 地図データは map-compare-infra、ライブラリは map-compare-library、検索とルート検索は map-compare-arch の [search](../../map-compare-arch/references/capabilities/search.md) と [routing](../../map-compare-arch/references/capabilities/routing.md)。棚卸しの項目ごとに移行先の対応 (そのまま、置き換え、やめる) を表にする。
4. 費用を並べる: map-compare-infra の [criteria](../../map-compare-infra/references/criteria.md) の「費用の見積もり方」で、今の規模と 1 年後の規模について新旧を並べる。移行の作業の費用と、移行中に両方へ払う期間の費用も足す。
5. 帰属表示を決める: 移行先の帰属表示の文言と置き場所を [attribution](../../map-legal-check/references/attribution.md) で決める。移行元のロゴと文言を外す時期は、移行元の地図を出さなくなった時期と合わせる。
6. 試作して比べる: 代表的な画面を移行先で作り、場所とズームを決めて並べる。検索は代表的な入力 (住所、施設名、表記の揺れ) で結果を比べる。地図の読み込み時間と、低性能の端末での動作も測る。
7. 段階を決める: 例として、(1) 社内だけ、(2) 利用の少ない画面、(3) 利用者の一部、(4) 全員、(5) 移行元の停止。各段階に、進む条件 (エラー率、読み込み時間、問い合わせ) と戻す条件を書く。
8. 戻し方を用意する: 各段階で、フラグを戻せば移行元に戻る状態を保つ。移行元の API キーと契約は、最後の段階まで止めない。移行先で新しく作ったデータ (移行先のジオコーダで付け直した座標) は、移行元に戻しても捨てずに残せるように分けて保存する。
9. 移行元を止める: 全員を移したら、移行元の SDK とコードを消し、API キーを無効にし、移行元に由来するキャッシュと保存データを規約に従って消す。消したことを記録に残す。
10. 公開の前に map-legal-check で帰属表示と規約を確かめる。

## 落とし穴

- 地図だけ先に移し、検索やルート検索を移行元に残す計画は、Google からの移行では規約上とれない ([from-google-maps](from-google-maps.md))。最初の段階から検索の移行先も用意する。
- 移行元の SDK が送っていたテレメトリや地図の利用の計測が、移行後に消える。分析の指標が途切れないよう、自前の計測を移行の前に入れる。
- 戻せる期間に移行元の費用が続く。両方に払う期間を費用に入れる。
- ネイティブアプリで、古い版が移行元の API キーを使い続ける。止める前に利用者の割合を見て、強制アップデートの要否を決める。
- 見た目の差は利用者の問い合わせとして出る。何が変わるか (配色、POI の出方、検索の結果) を先に知らせる。

## ライセンス上の注意

コピーレフト (GPL、LGPL、AGPL)、OSI 非承認、データの継承条件 (ODbL など) があるものは、組み込み、改変、配布、SaaS 提供のそれぞれで何が求められるかを書く。

- 移行先のライブラリ、プラグイン、地図データのライセンスは、各移行元の reference と map-compare-library の reference で確かめる。移行で OSM 由来の地図データに替えるなら ODbL の帰属表示と、抽出したデータを配るときの継承条件がかかる ([odbl](../../map-legal-check/references/odbl.md))。
- 自作の抽象化層を OSS として公開するときは、包んだライブラリのライセンス (Mapbox GL JS v2 以降は OSS ではない) と矛盾しないかを確かめる。
