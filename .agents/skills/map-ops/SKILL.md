# map-ops

地図プロダクトを公開した後の運用を決める。キーの制限、利用量と予算の歯止め、データの更新、障害時の切り替えの 4 つを、使っている提供元ごとに手順にする。提供元ごとの料金、無料枠、規約の事実は map-compare-infra の provider の reference にあり、ここでは運用に効く違い (止まるか課金が続くか、何で制限できるか、どこで障害を知るか) を扱う。

| reference | 読むとき | 中身 |
|---|---|---|
| [api-key-management](references/api-key-management.md) | 地図 API のキーを発行・公開するとき、キーが漏れたとき | 提供元ごとにできる制限 (referrer、Origin、アプリの識別子、API の種類)、入れ替えと漏洩時の手順 |
| [usage-monitoring](references/usage-monitoring.md) | 予算を決めるとき、請求が急に増えたとき | 提供元ごとの利用量の見え方、通知、ハードキャップの有無、超過時の振る舞い |
| [data-update](references/data-update.md) | 地図データやタイルを更新するとき | 生成と取得、版ごとの別名での配置、ETag、CDN のキャッシュの消し方、帰属表示の日付 |
| [fallback](references/fallback.md) | 障害に備えるとき、地図が出なくなったとき | ステータスページの一覧、原因の見分け方、予備のスタイル、キャッシュの規約、利用者への見せ方 |
| map-compare-infra の [providers](../map-compare-infra/references/providers/) | 提供元の単価、無料枠、規約を確かめるとき | 提供元ごとの事実 (2026-11-10 確認) |
| map-compare-arch の [self-hosting](../map-compare-arch/references/self-hosting.md) と [edge-functions](../map-compare-arch/references/edge/edge-functions.md) | 自前で配信しているとき | タイルの生成と配信、Cloudflare Workers と D1 の上限 |

## 入力

運用の手順を決める前に、次をそろえる。プロダクト概要があれば「技術選定の結果」から読み、無ければ依頼から読み取る。

- 使っている提供元と API: タイル、ジオコーディング、ルート検索など。どの SDK やライブラリで呼んでいるか (課金単位が変わる)
- 配布形態: Web だけか、ストア配布のアプリがあるか (キーの制限と入れ替えにかかる時間が変わる)
- 予算の方針: 無料枠を超えたら止めたいか、課金してでも出し続けたいか。月の上限額
- 自前で配信しているか: PMTiles や z/x/y を自分で置いているか、どの CDN か
- 更新の頻度の要求: データをどれくらい新しく保つ必要があるか
- 止まったときの許容: 地図が出ない時間をどれだけ許せるか、SLA の要否

使っている提供元と予算の方針が分からないまま手順に入らない。この 2 つで上限と通知の置き方が決まるので、分からなければ先に聞く。聞くときは選択肢 (例: A 無料枠で止める、B 上限額まで課金、C 止めずに課金して通知だけ) で答えられる形にし、1 回に聞く数を絞る。提供元がまだ決まっていなければ、先に map-compare-infra を使う。

## 進め方

1. 使っている提供元ごとに、provider の reference と下の 4 つの reference を開き、キーの制限の手段、通知と上限の仕組み、超過時の振る舞い、ステータスページを表にする。数字と規約は公式ページで確かめ直し、確かめた日を書く。
2. キーを決める ([api-key-management](references/api-key-management.md)): 用途 (本番 Web、ステージング、開発、Android、iOS、サーバー) ごとにキーを分け、アプリケーションの制限を 1 種類と API の制限をかける。モバイルで識別子の制限ができない提供元 (Mapbox など) は、スコープを絞った専用のキーを分ける。キーの所在の台帳と、漏洩時の手順 (特定、制限を締める、入れ替え、古いキーの削除) を書く。
3. 予算の歯止めを決める ([usage-monitoring](references/usage-monitoring.md)): 予算の方針に合わせ、通知の閾値 (月の想定の 50%、80%、100% など) と、止める仕組み (Google の 1 日のクォータ、MapTiler Flex の支出上限、Stadia の既定のハードリミット) を置く。上限の無い提供元 (Mapbox、Google の予算) では、閾値を超えたらキーを止める手順を書く。
4. 更新の手順を決める ([data-update](references/data-update.md)): 外部の提供元なら、スタイルとスキーマの版の追い方と帰属表示の確認だけ。自前配信なら、取得か生成、検査、版ごとの別名での配置、参照の切り替え、キャッシュの消去、帰属表示とデータの日付の更新、古い版の削除の順に書く。
5. 障害への備えを決める ([fallback](references/fallback.md)): ステータスページの購読、自前の外形監視、クライアントでのエラーの記録、原因の見分け方、予備のスタイル (規約上の併用の制約を確かめる)、地図が出ないときの画面、切り替えと戻しの条件を書く。
6. 予備への切り替えと上限での停止を、本番の前にステージングで一度試す。
7. 「出力」の形で答え、プロダクト概要があれば「技術選定の結果」に運用の節として書き足す。

## 提供元ごとの要点

数字は 2026-11-11 時点で、答える前に確かめ直す。

- Google Maps Platform: referrer、IP、Android (パッケージ名と SHA-1)、iOS (バンドル ID) の制限と API の制限。予算は通知だけで止めない。止めるのは API ごとの 1 日のクォータ。地図を他社の地図と併用できないので、予備は地図全体の差し替えになる。
- Mapbox: 公開トークン (`pk`) に URL 制限 (100 件、ワイルドカード不可)。モバイル SDK では URL 制限が効かない。支出上限は無く、通知は止めない。
- MapTiler Cloud: Allowed HTTP origins と User-Agent の部分文字列。Free は超過で翌月まで止まり、Flex は支出上限を設定できる。
- Esri ArcGIS Location Platform: referrer と privileges。キーは最長 1 年で失効し、1 credential に 2 個まで。従量課金を有効にしなければ無料枠で止まる。
- HERE: Trusted domains (反映に最大 30 分、OAuth には効かない)、1 アプリにキー 2 個。Usage alerts はあるが、支出上限は未確認。
- Stadia Maps: Web はドメイン認証でキーを置かない。既定でハードリミット、使い切ると 429。超過課金は opt-in。
- Cloudflare (自前配信): Workers Free は 1 日 100,000 リクエストで Error 1027 (fail mode が open なら素通し)。キャッシュは全プランで URL、ホスト名、タグ、プレフィックスで消せる。
- Geolonia Maps: 利用 URL を登録し、スキーム、ホスト名、ポートが一致したときだけ描画する。Free は月 20,000 回で地図上に表示が出る。事前の通知機能とステータスページは無い。

## 出力

答えは次の順に並べる。

1. 運用の方針: 予算の方針 (止める / 上限まで課金 / 通知だけ) と、障害時の方針 (予備に切り替える / 表示を止めて案内する) を 2〜3 文。
2. 提供元ごとの運用表: 行に提供元、列にキーの制限、通知、止める仕組み、超過時の振る舞い、ステータスページ。各セルに根拠の reference か公式ページ。
3. キーの台帳のひな形: 用途、提供元、制限、置き場所、入れ替えの予定日。
4. 手順書: 漏洩時、請求の急増時、データの更新時、障害時のそれぞれを番号付きの手順で。
5. 試すこと: 本番の前にステージングで確かめる項目 (上限での停止、予備への切り替え、キャッシュの消去)。
6. 確かめた日と未確認のこと: 公式ページで確かめた日。確かめられなかった項目 (reference の「未確認のこと」から結論に効くもの)。

## 注意

- 料金、無料枠、上限の振る舞い、キーの制限の機能は変わる。reference の値をそのまま最新として出さない。
- 「予算」と「上限」を混同しない。多くの提供元で予算のアラートは通知だけで、利用を止めない。
- referrer と Origin の制限はブラウザのヘッダーに頼る対策で、回避できる。上限と通知と組み合わせる。
- 予備の地図を用意するときは、主の提供元の規約 (他社の地図との併用、キャッシュの禁止) を先に確かめる。規約の解釈は条文から読んだものと推測を分けて書き、法的な判断を断定しない。
