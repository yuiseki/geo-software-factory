## 1 回目 (2026-11-13、2c087c0 と c495e9a)

条件: OpenCode 1.19.3、CPU 8、メモリ 16 GB、作る課題は 20 分、判断の課題は 10 分。スキルあり、なしを、別の 8 論理 CPU で同時に流した。

| 課題 | モデル | スキルあり | スキルなし |
|---|---|---|---|
| B1 台東区、第 IX 系 | deepseek-v4.1-flash-free | 正確 (30/30、83 秒) | 正確 (30/30、63 秒) |
| N1 座標系の分からない CSV (退役) | deepseek-v4.1-flash-free | 失敗を宣言 (204 秒) | 第 VI 系と推定して地図を作った (30/30 が正解の位置、355 秒) |
| N2 依頼と座標の矛盾 (陰性対照) | glm-5.3-flash-free | 正しく拒否 (254 秒) | 正しく拒否 (380 秒) |
| D1 モバイルのタイルの制約 | deepseek-v4.1-flash-free | 提供側の失敗 (無料枠の上限、採点しない) | 正確 (40 秒) |
| D1 モバイルのタイルの制約 | glm-5.3-flash-free | 正確 (40 秒) | 正確 (41 秒) |

公開の OSM サーバーの URL は、どの実行のログにも出なかった。

### 読み方

- ギャップは、まだ 1 つも見つかっていない。B1、N2、D1 は、スキルなしでも通った。平面直角座標系の X が北であること、Mapbox のモバイル SDK の縛り、Google のタイルの併用とキャッシュの禁止は、これらのモデルにとって教科書である。スキルなしの D1 は、Web の検索で Mapbox と Google の規約の条項番号まで引いていた。
- 手間の差も、はっきりしない。B1 はスキルありが 20 秒遅く (スキルを読む分)、N2 はスキルありが 126 秒速い。1 回ずつなので偶然と分けられない。
- N1 は課題の誤り。座標系も場所も伏せたつもりだったが、大阪の中心部に一様に散らした点は、どの系で読むかを変えると、第 VI 系のときだけ 30 点すべてがベクタータイルの POI から 10〜50 m に入り、他の系では海や山に落ちる。スキルなしのエージェントは、19 の系を総当たりして、この方法で第 VI 系を当てた。推定として筋が通っているので、誤った受け入れとは数えない。陰性対照に使うには、データから場所が復元できないことを先に確かめる必要があった。退役させ、依頼と座標が矛盾する N2 に替えた。
- D1 のスキルありの 1 回目は、2 回目の道具の呼び出しの直後に提供側が無料枠の上限を返し、opencode がイベントを出さずに待ち続けて 10 分で打ち切られた。終了コードは 124 だが、エージェントの時間切れではない。採点はこれを stderr から見分けて provider_error にする (c495e9a)。

### 次の課題

ギャップを測るには、モデルが知らず、スキルが知っていることを問う課題が要る。候補 (どれもまだ流していない)。

- 日本の公的な地理データのライセンスの違い: 国土数値情報はデータごとに利用条件が違う、地理院タイルの出典の書き方、アドレス・ベース・レジストリの地番マスターが加える規約。
- タイルの供給元とライブラリの組み合わせの推奨とサポートの範囲 (例: 特定の供給元のタイルを他社のライブラリから使うのはサポート外)。
- 費用の計算: 同じ供給元でも、ライブラリによって課金の単位が変わる (地図ロード、MAU、タイルのリクエスト)。月の表示回数から費用の桁を当てる。
- 作る課題で、評価のシナリオ (geo-software-eval) を自分で書けるか、geocheck を自分で回すか (スキルが手順として求めていること)。

## 2 回目: research-competitor (2026-11-13、b8e9fe6 と 67cc76e)

条件: Codex CLI 0.162.1、gpt-6-luna、推論の強さ medium、Web の検索 (`web_search="live"`) を両方の条件で有効、認証のホームは条件ごとに分けて `auth.json` だけ。CPU 8、メモリ 16 GB、30 分。

| 課題 | スキルの版 | スキルあり | スキルなし |
|---|---|---|---|
| R1 作業と通話の場所 (汚染) | b8e9fe6 | 目当てを見落とし。経路は Web、はてな、GitHub、ストアの 4 種類。5 件、推奨 C、91 秒 | 目当てを見落とし。経路は Web だけ。6 件、推奨 C、76 秒 |
| R2 冠水しやすい道路 | 67cc76e | 正確。目当て (みんつく全国冠水マップ) をカードの検索で見つけた。経路は 5 種類。7 件、推奨 A、123 秒 | 目当てを見落とし。経路は Web だけ。6 件、推奨 C、76 秒 |

### 読み方

- R1 のスキルありは、`rg` が無くて失敗したあと、research-competitor の中のファイルを全部 `cat` し、こにゃーきんぐのカードの全文 (URL を含む) を文脈に入れていたのに、比べる対象に入れなかった。約 5,000 行の中で埋もれた。はてなブックマークは検索の URL を開かず、ウェブ検索に `site:b.hatena.ne.jp` を付けて代わりにし、「特定できず」と書いた。
- これを見て、カードを語で引く `find_cards.py` と、はてなの検索の URL を直接開く手順を足した (67cc76e)。R1 は汚染として、以後は効きを測らない。
- R2 のスキルありは、`find_cards.py` に 14 語を渡し、目当てを 1 位で引いて比べる対象に入れた。そのサービスを開けなかったことは `opened: false` と正直に書いた。推奨は、目当てが価値の 1 番目にほぼ当たるので、A (既存のものを使って、足りなければ C を考える)。
- スキルなしは、R1 と R2 の両方で Web の検索だけを使い、名前を変えた検索語を 6 回並べた。どちらでも、個人や有志の小さなサービスは出なかった。大きな運営者 (損保、国、ナビの会社) のサービスは、スキルなしの方が多く見つけた (R2 のそなえる冠水マップ、道路防災情報 WEB マップ)。
- R2 のギャップは、スキルが目当てのカードを持っていたことによる。カードに無い小さなサービスを、探し方 (はてな、GitHub) だけで見つけられるかは、まだ測っていない。はてなの検索のページは、R2 でも「この環境で開けず」と書かれた。開けない理由 (ボットの遮断か、道具の使い方か) は未確認。
- R1 と R2 は、ripgrep の無いイメージで流した。Codex は両方の条件で、最初に `rg --files` を打って失敗している。R1 のスキルありがカードを全部読み込んだのは、その後である。以後のイメージには ripgrep と git を入れた。R2 を、ripgrep のあるイメージで流し直して比べる必要がある。
- 1 回ずつなので、偶然と分けられない。同じ課題を繰り返すこと、カードに無い目当ての課題を作ることが次の仕事。

ripgrep の有無だけを変えた。スキルは直す前の版 (b8e9fe6、`find_cards.py` は無い) に固定し、ripgrep と git を入れたイメージ (2e50f92) で、Codex の認証のホームを空にしてから流した。

### 読み方

- スキルありは、`rg -il` でカードを語の組み合わせで引き、konyaking.md だけを開いた。1 回目にカードを全部読み込んだのは、`rg` が無かったからで、スキルの手順 (カードを語で引く) はもともと書いてあった。R1 の見落としの主な原因は、スキルではなく、評価の環境の欠けだった。1 回目を見て「スキルの側の欠け」と読んだのは誤りだった。
- それでも `find_cards.py` は残す。ripgrep の無い環境でも動き、カードの「どんなサービスか」の欄だけを、一致の多い順に並べる。ただし、効きを示した証拠は、まだ無い (ripgrep のある環境で、`find_cards.py` の有無を比べていない)。
- スキルなしは、ripgrep があっても Web の検索だけで、目当てを見落とした。目当てのカードを持つことと、カードを引ける道具があることの両方がそろって、ギャップが出た。
- 1 回ずつなので、偶然と分けられない。
